---
name: ritual
description: Turns the errors of a session into lessons, rules, guard hooks and tests, and keeps the project's lessons sharp. Use at the end of a session, after a painful bug, or before calling a feature done (`/ritual close`). On a project without `.ritual/`, it sets Ritual up first. Always reply in the user's language.

# /ritual

Every mistake becomes a lesson, every lesson a rule, and every rule, when it can, a check. A rule that only lives in text gets forgotten in a long session; a guard or a test does not.

Reply in the language the user writes in. Lessons are written in the project's language (`.ritual/config.json` → `language`). The plugin's lessons live in `lessons/<language>/`, falling back to `lessons/en/`, the original, while a translation is missing.

Paths below use `${CLAUDE_PLUGIN_ROOT}`, the folder where Ritual is installed. All scripts are Node; run them with `node`.

## Which mode

- The project has no `.ritual/` folder → **Setup**, then stop.
- The user wrote `/ritual close` (or `/ritual cierre`, or asks for a check before finishing) → **Close review**.
- The user wrote `/ritual doctor`, or says Ritual does not work (no questions show up, the guard does not block) → **Doctor**.
- The user wrote `/ritual share` (optionally with a lesson id), or wants to contribute a lesson or a confirmation → **Share**.
- Otherwise → **Ritual**.

## Doctor (`/ritual doctor`)

Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/doctor.mjs"` and show its output as is. It checks Node, the plugin's library, `.ritual/` (config, guard rules, own lessons) and whether the hooks ran in this session. For each ✕ line, explain the fix in plain words and offer to do the part you can (a broken `.ritual/config.json`, a guard rule whose case fails, a malformed lesson). Installing Node, enabling the plugin and restarting Claude Code are the user's to do. Run it again after a fix. Write nothing else.

## Setup (first run in a project)

1. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/init.mjs" --detect`. It prints what the project says about itself (its README and folders), the packages its dependencies turn on, every package with what it `covers`, and the language it guesses.
2. Work out, without asking: one generic line about what the project is (`about`: the kind of project and who it is for, such as "a programming course for beginners" or "an internal sales dashboard"; no client, product or people names), and the packages whose `covers` fit, by dependencies **or** by what the project is. A course has no dependency that gives it away; its README does. Also list the names that would identify the project in a shared lesson and that the automatic check can't guess: a client, a product, a sample company or dataset used in examples, a person's name or nickname (`private`).
3. Ask the user **one** question: confirm the `about` line, the packages, the `private` names and the language, with half a line on why each package fits. Say why it matters, once: each package adds the lessons for that kind of project, so its typical mistakes get caught, and the packages left off cost no tokens.
4. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/init.mjs" --packages <list> --language <code> --about "<line>" --private "<name>, <name>"`. It creates `.ritual/` (config, guard rules, own lessons folder, candidates), adds `.ritual/local/` to `.gitignore` and a short Ritual section to `CLAUDE.md`. Running it twice changes nothing; running it later with new `--packages` or `--about` updates them.
5. Tell the user in three lines what was created and that the hooks are now active: the package lessons are given at each session start, the guard blocks commands that already failed, the log records failed commands and corrections, each group's detector questions appear once per session (and again after a compaction), Haiku picks in the background the lessons that apply to each request and each new file (`"picker": false` turns that off), and `"close": true` in the config turns on an automatic close: the first time Claude is about to finish after changing files, it goes back once to check the work by running it (off by default; `/ritual close` does it by hand). The log starts today: if the project kept notes of earlier mistakes (its own lessons, a previous ritual, a candidates list), say in one line that the first `/ritual` should read them too.

## Ritual

Start with `node "${CLAUDE_PLUGIN_ROOT}/scripts/summary.mjs"`. It prints, compactly, everything since this session's last ritual: failed commands, user corrections (with what was being touched) and the reports of the agents that ran in the background from the log, the guard's blocks, the open candidates, and the groups touched. When other sessions log into the same project (another person, another branch, another worktree), it counts their entries in one line and leaves them for their own ritual: they are not this ritual's errors, so do not treat or mark them, unless the user asks to review them too (`--all`). Read it completely; do not rebuild it from memory.

Then follow the steps in order. Each step produces one or two lines for the user; the whole ritual is a report, not a conversation. Ask only when a cause cannot be confirmed.

- **Context first.** Read `about` and `packages` in `.ritual/config.json`. If `about` is empty, write it from the README and this session, as in Setup step 2, and confirm it in the same one question as anything else. If this session shows a kind of project whose package is off (exercises and quizzes → `education`, model calls → `ai`, a login and a database → `apps`, scenes and narration rendered with code → `video`), propose turning it on in one line, with the reason. Never turn one on without a yes; apply it with `init.mjs --packages <list>`.
0. **Open candidates.** For each open candidate in `.ritual/candidates.md`: can it become a test or a guard rule today? If yes, do it (step 5). If not, leave it `open` or mark it `discarded` with the reason. Candidates are never deleted.
1. **List the errors.** From the log first (read each agent report in whatever language it is: a reviewer's or a QA agent's must-fix findings are errors; a search or a summary is not), then the conversation, then the commits. For each one: what happened and its cause, confirmed by looking, not guessed. A correction in the log gives the phrase and what was being touched; finding the cause is your job. A missed first step (the summary's `First step after a request` line) and a failed picker rule (its `Picker rules` line: a rule skipped a file that had lessons) are Ritual's own failures, not the project's: say how many and why in one line of the report, so the user can tell the maintainer; `summary.mjs --first-steps` counts every one since the start.
2. **Which lesson covered it, and why it did not fire.** Look first in the group of what was being done: the plugin's `lessons/<language>/<group>.md`, then the project's `.ritual/lessons/<group>.md`. Sharpenings and new lessons also carry `origin: field · <model> · <YYYY-MM>`. If a lesson covered it, that is a false negative: sharpen its detector question or its warning sign, or add the example. Plugin lessons are never edited in place: write the sharpening as a project lesson in `.ritual/lessons/<group>.md` (on a branch, its own file: see **Which file** in step 4) with `` `refines: N` `` in its data line, so the hook shows its sharper question in place of the original's (`lessons.mjs --check --project` rejects a `refines` that names no lesson).
3. **False positives.** Questions that made you stop or ask without need, and guard blocks that were wrong (`node "${CLAUDE_PLUGIN_ROOT}/hooks/guard.mjs" --log`). A wrong block becomes an `allows` case of that rule in `.ritual/guard.json`. A question that never applies to this project goes to `demoted` in `.ritual/config.json`, which is reversible. Nothing is deleted.
4. **New lessons**, only for an error no lesson covers. Five parts (see `${CLAUDE_PLUGIN_ROOT}/lessons/TEMPLATE.md`), `` `origin: field · <model> · <YYYY-MM>` `` with your own exact model id (the one this session runs on, e.g. `claude-opus-5-5`) and the month the mistake happened, the id that `node "${CLAUDE_PLUGIN_ROOT}/scripts/lessons.mjs" --next-id` gives (it looks in every branch and worktree, so two people writing lessons at once do not take the same number), in the file of the group of what was being done. Use `about` to write it precisely: the example in this kind of project's terms (without naming it), and a `packages:` line when the mistake belongs to that kind of project alone. Before writing it, instantiate it in two other kinds of project: if the text alone does not say what to do there, it is incomplete. No detector question, no lesson: it may be a note for the docs of the area it touches.
   **Which file.** On the project's main branch, `.ritual/lessons/<group>.md`. On a branch that will be merged later (another person, another worktree), the branch's own `.ritual/lessons/<group>.<branch>.md`: the hooks read it as the same group, and two branches that add lessons at once never edit the same file, so joining them never conflicts. The same goes for a sharpening: on a branch, never edit a lesson that lives in another file; write a new lesson in the branch's file with `` `refines: <its id>` ``.
   **New segment?** Plain source code outside every group is expected (the default patterns leave out `*.py`, `*.ts`, `src/` and the like): it is no reason to ask, and it is not moved into a group just to clear the line. Ask before writing each new lesson, and when the summary's `Files outside every group` shows a folder or a file type that looks like a different kind of work (scenes and narration, firmware, game levels): decide whether this work fits the existing groups and packages, and write the answer in one line, with its reason either way, so whoever reviews it later can disagree: «New segment: no · <the group and package it fits, by their `covers`>» or «New segment: yes · <slug>: <what it would cover> · <which `covers` it fails, and why>». A file outside every group that does fit a group is a missing pattern, not a new segment: add it to `groups` in `.ritual/config.json` and say so. Say yes only when a lesson from this session fails the transfer test against every package's `covers`: one tool or one file type is not a kind of project. Then add an `open` candidate «New package <slug>: <covers>. Detect: <one to three dependencies, or none>», with the reason, and keep the lesson in the project without `packages:` (the checker rejects a package that is not in the library yet); `/ritual share` proposes it to the library (step 6.4). A new group needs three lessons, so it waits in a candidate until then.
5. **Up the ladder.** For each lesson that fired today, new or sharpened, ask: can a check run alone?
   - A command pattern → a rule in `.ritual/guard.json` with `blocks` and `allows` cases. Run `node "${CLAUDE_PLUGIN_ROOT}/hooks/guard.mjs" --selftest` and see it block the real command before you trust it.
   - A property of the code or the output → a test named after the lesson, seen failing against the real error before the fix.
   - Neither → a one-line rule in the Ritual section of `CLAUDE.md`, only if the log shows it broke more than once. Otherwise it stays a lesson and goes to `.ritual/candidates.md` as `open`, with the date.
6. **Write everything together**, in the same commit: lessons, candidates, config and guard rules, the `CLAUDE.md` line. Then run `node "${CLAUDE_PLUGIN_ROOT}/scripts/lessons.mjs" --check --project .`; it must pass.
7. **Anonymous and on its way.** Examples name no clients, products or people. A lesson caught here is meant for the library, so none should stay local by being forgotten. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/share.mjs" status --apply`: it marks «Merged into N.» on the lessons the library accepted (so they are not shown twice) and lists the ones not shared yet. For each of those, and for any plugin lesson that fired because the mistake happened again, offer `/ritual share <id>` in one line. A lesson that only fits this project gets `` `local: <why>` `` in its data line instead, and is not offered again. Never publish anything yourself.

Close with the report. Write `.ritual/local/ritual-<YYYY-MM-DD-HHMM>.json` (the time keeps a second ritual on the same day from replacing the first one's report) with one entry per error from step 1, in any language for `what`:

```json
{ "date": "<YYYY-MM-DD>", "cost": "<optional, measured, e.g. $9.53 in reviews>", "errors": [
  { "what": "<one line>", "caught": "test|reviewer|validator|guard|user|other", "lesson": "<id or empty>", "action": "sharpened|new|none", "check": "done|open|none" }
] }
```

`caught` is what found it (`user` when the person had to correct it); `action` is what this ritual did to its lesson; `check` is whether it became a guard rule or a test (`done`) or a candidate (`open`). Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/summary.mjs" --report <that file>` and show its output as is: the script counts and draws, and adds the guard blocks and the candidates. Below it, at most three lines on what needs the user. Then `node "${CLAUDE_PLUGIN_ROOT}/scripts/summary.mjs" --mark` stamps the date of this ritual, after the report, which counts this session's guard blocks since its last one. The mark is for this session only: other sessions keep theirs (with `--all`, on both `--report` and `--mark`, if this ritual reviewed every session).

## Share (`/ritual share [lesson]`)

The goal: a lesson that helps someone building something else. A lesson written inside a project speaks in that project's terms ("the invoice importer"); shared like that, it helps nobody. Work through these steps, and tell the user in one line what each one decided.

1. **Which lesson.** The one the user named, or list the project's lessons in `.ritual/lessons/` and ask which. If what happened is already a plugin lesson that fired here, go to step 3.
2. **Compare first.** Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/share.mjs" context <group>` and read every library lesson it lists, plus the groups and packages with what each one `covers`. Compare by meaning, in any language.
3. **Already covered?** If a library lesson covers it, do not write a new one:
   - The mistake happened again: write the anonymous example to a file and run `node "${CLAUDE_PLUGIN_ROOT}/scripts/share.mjs" confirm <id> <your model id> <YYYY-MM> <file> "<measured>"` (the measured line of step 7). A confirmation is the most useful contribution: it records which models make the mistake.
   - Yours sharpens it (a better detector question, a missing case): share it with `Where it goes. refines <N>`.
4. **Make it generic.** Rewrite the idea, the detector question, the warning sign and what to do in terms of the mechanism that failed, not the domain where it failed: not "the invoice importer dropped the last page" but "a loop that stops at the first empty page assumes there are no gaps". Keep the example concrete, with nothing that identifies the project. Write it in English: shared lessons become the original.
5. **Transfer test.** Write, one line each, what the same mistake looks like in two other kinds of project. If you cannot, the lesson belongs to this project: say so, write `` `local: <why>` `` in its data line, and stop. Not every lesson is for everyone.
6. **Where it goes.** Stop at the first step that holds:
   1. It refines an existing lesson → `refines <N>`.
   2. The transfer test worked across different kinds of project → `core`, with its group.
   3. It only holds for one kind of project and an existing package `covers` it → `package <slug>`, and `packages: <slug>` in the data line.
   4. No package covers that kind of project → `new package <slug>: <what it covers>. Detect: <1-3 dependencies>`. Name it after the kind of project (`mobile`, `data`, `games`), never after a framework a package already covers (`nextjs` is `web`). Proposing a package is cheap: that is how the library grows to new kinds of software.
   5. The activity fits none of the groups' `covers` → `new group <slug>: <what it covers>`. Rare: a group is created when three lessons need it, so check the closest group twice before proposing one.
7. **Write and check.** Save the lesson to `.ritual/local/share/<id>.md`: heading `### <title>`, the data line (`origin: field · <your model id> · <YYYY-MM>` and `groups:`, `packages:` as decided), the five parts, then `**Where it goes.**`, `**Transfers to.**` (two lines) and `**How to reproduce.**` (a short task or prompt, no logs, paths or data from the project), and `**Measured.** caught: … · fired: … · recurred: … · cost: …`, from what was recorded: `caught` (test, reviewer, validator, guard, user or other) and whether a lesson existed (`fired`: no lesson, showed up, did not show up) from the ritual's report file and the log, `recurred` from how many findings had the same cause, `cost` only if it was measured (a reviewer's usage, read after it ended). Anything not measured is `unknown`, never an estimate; show the line to the user before sending. Run `node "${CLAUDE_PLUGIN_ROOT}/scripts/share.mjs" check <file>` and fix what it reports: it rejects names from the project (package name, folder, git remote, `private` in `.ritual/config.json`), a missing part or model, and a package or group that does not exist and is not proposed.
8. **Hand it over.** Show the user the final text and the link the check prints. The link also carries the kind of project: the packages on in `.ritual/config.json` (never the `about` line, which can name the project); if they look wrong for this project, fix them first, as in **Context first**. They open it, read it, and submit it themselves. Never submit it, never open issues or pull requests for them. When they say it is submitted, write `` `shared: <YYYY-MM-DD>` `` in the local lesson's data line (or its issue link, if they give it): each ritual then checks whether it was accepted, and marks it merged when it was.

## Close review (`/ritual close`)

Before calling a feature done. Read the groups touched from `node "${CLAUDE_PLUGIN_ROOT}/scripts/summary.mjs" --groups` and walk the detector questions of those groups (plugin and project lessons) against the change just made. For each question: **does not apply** (say why in half a line), **applies and is answered** (where the evidence is), or **applies and is not answered** (this blocks "done": say what is missing). Blocking ones first. For every answered question that can be a test, propose the test **named after the lesson**. Do not declare the feature done while a question is unanswered; if the user closes it anyway, add it to `.ritual/candidates.md` with the date and when it will hurt.
