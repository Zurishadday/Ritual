# シミュレーション

[English](README.md) · [Español](README.es.md) · [Português](README.pt.md) · [Français](README.fr.md) · [中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

パッケージ（`web`、`apps`、`crm`、`ai`）のレッスンは作り話ではありません。モデルが何かを作り、それを壊すのを観察して得られたものです。各シミュレーションは、顧客が依頼するような書き方で書かれた現実的な課題で、モデルが Ritual を使わずに作ります。その後、別のセッションの別のモデルが、作られたものを実行し、何が壊れたかを証拠とともに記録します。壊れたものは `origin: lab · <モデル> · <年-月>` を付けたレッスンになります。壊れなかったものは入りません。

## 方法

1. **構築**：機械的なモデル（Sonnet）が、きれいなフォルダの中で、`TASK.md` の文章をそのまま使い、それ以外は何も使わずに作ります。このモデルは、レッスン、フック、このフォルダを見ることはありません。
2. **レビュー**：判断を行うモデル（Opus）が、別のセッションで、`REVIEW.md` を使って行います。作られたものを実行し、人が実際にたどる経路を試します（空の入力、エラー、ダブルクリック、モバイル、キーボード）。そして、爆発はしないが依然として誤っているもの（パスワード、エスケープされていないテキスト）を探します。各発見には証拠が付きます。コマンドとその出力、あるいは画面で見たものです。レビュアーは何も修正しません。
3. **レッスンの作成**：同じ判断を行うモデルが、五つの部分で書きます。その後、リポジトリの人間のレビュアーが取り込みます。コアですでに扱われていないかを確認し、チェッカーを実行します。
4. **各課題は二回実行されます。** 二回とも壊れたものはレッスンです。一回だけ壊れたものは候補のままです。

各実行は `<タスク>/runs/<年-月>-<モデル>-<n>/` に保存されます（`2026-10-sonnet-1`、`2026-10-sonnet-2`）。残されたままのコード（実際のバグを含む例のプロジェクトであり、そのレッスンのキャリブレーションの対象です）と `FINDINGS.md` です。

## シミュレーションを繰り返す方法

新しいモデルが出ると、課題は再び実行されます。もう壊れなくなったレッスンは削除されません。格下げされ（そのレッスンを使うプロジェクトの設定に `demoted` と記され）、実行の記録にも残ります。こうして、モデルが良くなるにつれ、ライブラリはデータに基づいて自然に小さくなります。

スクリプトがこれを行います：`node scripts/simulate.mjs <task>`（例：`web`）。Sonnet が構築し、Opus がレビューします。これを2回、それぞれ独立した Claude Code セッションで行い、スクリプトが実行結果を比較します。レッスンが説明する失敗が全実行で再発した場合、そのモデルで確認済みとなります。どの実行でも失敗が起きなかった場合、降格の候補になります。まず `node scripts/simulate.mjs --probe` で隔離を確認してください。構築を担うモデルは CLAUDE.md、メモリ、プラグインを参照できてはならず、サイトを起動してアクセスできなければなりません。メンテナーが `/maintain` で適用するまで、ライブラリは何も変更されません。

新しい課題を提案するには、課題の文章と、それが表すプロジェクトの種類を書いて issue を開いてください。

## Ritual は役に立つか？ web 課題での A/B 比較

同じ課題（スペイン語の web 依頼）、同じ構築者（`claude-sonnet-5-5`）、同じレビュアー（`claude-opus-5-5`）で、2026-10 に Claude Code 2.1.295–2.1.296 を使って行いました。まず Ritual なしで行い、次に Ritual のフックを読み込み、`web` パッケージでプロジェクトを設定して（`--with-ritual`）行いました。その後に手直しを行いました。同じ構築者が、Ritual なしで、構築物についてレビュアーの指摘を受けて修正します（`--fix`）。これにより、構築のコストと、残った問題を直すコストを合計で比べられます。

| | レッスンが扱う誤りが出た（9件中） | 新しい誤り | 構築 | 見つかったものを修正 | 構築 + 修正 |
|---|---|---|---|---|---|
| Ritual なし ([1](web/runs/2026-10-sonnet-5-5-1), [2](web/runs/2026-10-sonnet-5-5-2)) | 7, 8 | 6, 7 | $0.28, $0.27 | $0.53, $0.45 | **$0.82, $0.72** |
| 質問のみ ([1](web/runs/2026-10-sonnet-5-5-ritual-1), [2](web/runs/2026-10-sonnet-5-5-ritual-2), [3](web/runs/2026-10-sonnet-5-5-ritual-3)) | 6, 9, 8 | 4, 4, 7 | $0.26, $0.27, $0.27 | | |
| 現在の Ritual あり ([1](web/runs/2026-10-sonnet-5-5-ritual-v2-1), [2](web/runs/2026-10-sonnet-5-5-ritual-v2-2), [3](web/runs/2026-10-sonnet-5-5-ritual-v2-3)) | **1, 2, 2** | 4, 5, 4 | $0.38, $0.53, $0.60 | $0.24, $0.17, $0.29 | **$0.63, $0.70, $0.90** |

この結果が示すこと：

- **誤り：** 9 件のレッスンが扱う誤りは、Ritual なしでは構築ごとに平均 7.5 回、Ritual ありでは 1.7 回出ました。約 4 分の 3 少なくなっています。レッスンの外にある新しい誤りは、6.5 から 4.3 に減りました。
- **コスト：** Ritual を使った構築は高くなります（構築 1 回あたり約 $0.23 多く、レッスンに合わせて設計し、確認のために一度戻るからです）。残ったものの修正は約半分のコストです（金額で −52%、出力トークンで −53%。平均で 24,300 対 11,300）。構築と修正を合わせると、ほぼ同じです。平均で $0.77 対 $0.74 で、この差は実行ごとのばらつきより小さいものです。同じ金額で、構築の時点で誤りがはるかに少ない成果物から始まります。
- **質問だけでは何も変わりませんでした。** 作成中に各グループの質問だけを表示したバージョンは、Ritual なしの構築と同じ所に終わりました。結果を変えたのは、開始時と終了時のパッケージのレッスンです。これにより、構築者は完了前に一度戻されます。

示さないこと：課題は一つ、各群の実行は 2 回か 3 回、モデルも一つです。誤りを見つける作業のコストは数えていません。レビューは構築 1 回あたり $1.30–$2.40 かかり、両群で同じです。各構築と修正のうち、このことに言及しているものはすべて、両群とも、試したコマンドでシェルが拒否されたと記しています。そのため、どれもサイトを実行しませんでした。終了時の自動 web チェックは一度も動かず、修正も再レビューされていません。

## 寄稿されたレッスンの確認

Ritual は Claude Code の中で動くため、レッスンは、そのミスが Claude と一緒に起きた場合にだけ、誰かのセッションで質問を得ます。寄稿されたレッスンと確認のたびに、どのモデルで、何月に起きたかが書かれています。

1. **Claude で、実際のプロジェクトで、その例とともに起きた：** そのモデルとともに `field` として取り込まれ、通常のレビュー（五つの部分、匿名、まだカバーされていない）を経ます。
2. **別のモデルで起きた、あるいは例が疑わしい：** メンテナーが状況を小さな課題に変えます。顧客の依頼のように書き、上記の方法と同じく、現在の Claude モデルで実行します。
   - Claude で壊れる：その Claude モデルとともに `lab` として取り込まれ、寄稿者のモデルは `seen:` に入ります。
   - 別のモデルでのみ壊れた：issue の中で候補のまま残り、そのモデルが記されます。誰かがそれが Claude で起きるのを見るまで、その質問は誰にも届きません。
3. **既存のレッスンの確認**は、`<モデル> <年-月>` を `seen:` に追加します。複数のモデルで見られたレッスンは一般的なミスです。古いモデルでしか見られなかったレッスンは、格下げの前に、新しい実行がまず確認する対象になります。
