# Git 与流程

适用于保存、结束、交接和协调的情形：提交、状态、待办事项和并行工作。

### 8. 把使用者列出来，不要靠记忆

`from: b3d4e214` · `by: ai`

**核心。** 当你改动一项数据，而其他人是按它的名字来读取时，谁在读它的清单必须写下来。记忆总会漏掉一个。

**例子。** 一个模型更新之后，三个屏幕上的标签都改了。第四个屏幕，没有人记得它，仍然提供上一个模型的选项。

**另一个例子。** 写一章的时候，凭记忆断言读者已经了解前一章的三个函数。搜索之后发现，那一章只教了一个，而另一章其实已经解释过被当作新内容来呈现的那个主题。

**再一个例子。** 一次改动在保存时，所写的文件清单是凭记忆列的，漏掉了一个：正是让新功能能够运行的那个文件。事后审查待提交改动的清单时，才发现了它。

**检测问题。** 我这份使用者的清单，是从搜索中得来的，还是凭记忆？

**警示信号。** “我已经覆盖了它使用的三个地方” · “他们已经看过了” · “我已经全部加上了。”

**怎么做。** 按改动类型保存一份影响地图。完整地过一遍，每一项都要说明“有改动”或“不适用，因为……”；如果改动产生了新的使用者，就在同一次改动中加上它。在引用一个来源之前，把你所断言的那句话从该来源中复制出来：别人说某人做了什么、看到了什么，也需要核对。

### 9. 同一种状态存在于多份记录中：要一起移动

`from: bc14d730` · `by: ai`

**核心。** 关闭一个待办事项通常涉及三个地方：待办列表、监视它的测试，以及描述它的文档。如果你只动了其中一个，其他两个就会与它相矛盾。

**例子。** 一个待办在列表中被标记为已关闭，但监视它的测试仍标着“预期失败”，而文档仍把它描述为未解决。三个地方，三个版本。

**检测问题。** 还有哪些地方声明了这种状态？在保存之前把它们都列出来。

**警示信号。** “我稍后再更新另一边。”

**怎么做。** 工作的单位是完整的一组，并且在同一次改动中完成。

### 30. 动手之前先解释，并等待同意

`from: 78e8a4b8` · `by: ai`

**核心。** 朝着错误的方向快速前进，并不是进步。

**例子。** 一个整个项目的文件夹结构在没有通知的情况下被重新组织了。这次改动本身是正确的，但它被完全撤销了，因为另一个人已经基于代码之外的理由决定了那个结构。

**检测问题。** 这个改动块是否很大、很难撤销，或者它会改变另一个人已经决定的东西？如果是，就解释并等待。如果不是，就说明你要做什么然后继续：每一步都请求许可，也是有代价的。

**警示信号。** “我已经知道他们想要什么了。”

**怎么做。** 在每个大块工作之前，用通俗的语言说明你要做什么、为什么做，然后等待确认。

### 35. 顺手记下的待办会过时

`from: 6deec922` · `by: ai`

**核心。** 你在做别的事情时记下的“以后再说”，可能已经不存在了，或者它原本就是一个有意的决定。

**例子。** 一条笔记写着“去掉日期筛选器”。等到真正去做时，这个筛选器已经是团队书面确定的决定了，去掉它会弄坏一份报告。

**检测问题。** 我今天检查过这一项吗，还是只因为它被写下来了，我就去做它？

**警示信号。** “它在待办列表上。”

**怎么做。** 在处理一个待办之前，先在今天检查它，并查找是否有书面决定说明它是被有意保留的。

### 40. 日志记录的是留下了什么、为什么留下，而不是失误的编年史

`from: 8309d6b7` · `by: ai`

**核心。** 变更历史是为了让人理解产品，而不是为了讲述做这次改动的人已经解决的失误。

**例子。** 一份历史写着：“试过 A，失败；试过 B，失败；保留了 C。”几个月后有人读它，他只需要 C 和它的理由，却不得不读完三段才找到它。

**检测问题。** 这一行是帮助人理解产品、避免重蹈覆辙，还是只是记录了发生在我身上的事情？

**警示信号。** “让我们把发生过的每件事都记录下来。”

**怎么做。** 写下最终状态及其理由。试过并失败的内容，只有在它能教会别人某件需要避免重复的事情时，才写进去。

### 47. 并行开展的工作会在共享部分发生冲突

`from: 3565a1b4` · `by: ai`

**核心。** 多人同时工作时，每个人都能清楚地看到自己负责的那部分。但他们共享的东西（测试、数据、整个项目的文档）会把各自的改动合并在一起：名字相互冲突，副本落后于原件，测试读取了别人尚未完成的工作。集成本身就是工作，不是粘贴。

**例子。** 四个人同时各自写一个部分，但把共享部分当作交付物。集成时，两个交付物使用了共享测试中已经存在的同一个名字，于是那个测试停止运行。另一个测试保留了它所检查内容的一份副本；部分改变了，副本却没有。一次测试运行因为另一个人仍在绘制的图片而失败。最后，每个部分都无法单独保存：共享文件里已经混入了所有人的改动。

**检测问题。** 哪两个部分同时在改同一个文件？谁来集成它？我的测试是否在读取别人尚未完成的工作？

**警示信号。** “我们每个人都测试了自己的部分” · “问题出在另一个部分。”

**怎么做。** 由一个人负责集成共享内容，并设置一个步骤，在名字冲突时停止。让测试读取原件，而不是副本。等所有人都完成后运行完整的测试套件，或者在排除仍在变动的部分后运行，并说明被排除的是哪些部分。把共享同一文件的部分一起保存，使每个保存的版本都能完整工作。
