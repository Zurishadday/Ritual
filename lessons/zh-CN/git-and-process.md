# Git 与流程

适用于保存、结束、交接和协调的情形：提交、状态、待办事项和并行工作。

### 8. 把使用者列出来，不要靠记忆

`from: 74a3645f` · `by: ai`

**核心。** 当你改动一项数据，而其他人是按它的名字来读取时，谁在读它的清单必须写下来。记忆总会漏掉一个。

**例子。** 一个模型更新之后，三个屏幕上的标签都改了。第四个屏幕，没有人记得它，仍然提供上一个模型的选项。

**另一个例子。** 写一章的时候，凭记忆断言读者已经了解前一章的三个函数。搜索之后发现，那一章只教了一个，而另一章其实已经解释过被当作新内容来呈现的那个主题。

**再一个例子。** 一次改动在保存时，所写的文件清单是凭记忆列的，漏掉了一个：正是让新功能能够运行的那个文件。事后审查待提交改动的清单时，才发现了它。另一次，一个提交称某些文件的副本“已经是最新的”，而其中三个文件其实缺失了；另一位审查者发现了这一点。

**检测问题。** 我这份使用者的清单，是从搜索中得来的，还是凭记忆？

**警示信号。** “我已经覆盖了它使用的三个地方” · “他们已经看过了” · “我已经全部加上了。”

**怎么做。** 按改动类型保存一份影响地图。完整地过一遍，每一项都要说明“有改动”或“不适用，因为……”；如果改动产生了新的使用者，就在同一次改动中加上它。在引用一个来源之前，把你所断言的那句话从该来源中复制出来：别人说某人做了什么、看到了什么，也需要核对。在写下某个副本“完整”或“已经是最新”之前，把它应当有的清单与它实际拥有的清单做一次比对。

### 9. 同一种状态存在于多份记录中：要一起移动

`from: d7a99bc7` · `by: ai`

**核心。** 关闭一个待办事项通常涉及三个地方：待办列表、监视它的测试，以及描述它的文档。如果你只动了其中一个，其他两个就会与它相矛盾。

**例子。** 一个待办在列表中被标记为已关闭，但监视它的测试仍标着“预期失败”，而文档仍把它描述为未解决。三个地方，三个版本。

**另一个例子。** 一个文本框由语音听写填充，听写的文字保存在一个单独的变量里，而发送按钮发送的正是这个变量。有人一边还在听写，一边手动删掉了前半段，结果整段文字都被发送了，包括已删除的部分。后来，发送之后文本框被清空了，变量却没有清空，于是下一次听写一开始，就带上了上一条消息的内容。

**检测问题。** 还有哪些地方声明了这种状态？在保存之前把它们都列出来。而我发送或保存的内容：它是来自人所看到的那份副本，还是来自旁边留存的一份副本？

**警示信号。** “我稍后再更新另一边。” · “变量里已经有文字了，我就发送它。”

**怎么做。** 工作的单位是完整的一组，并且在同一次改动中完成。发送或保存的内容要来自人所看到的那份副本，并且每一次发送或重置，都在同一行代码中清空所有副本。

### 30. 动手之前先解释，并等待同意

`from: a2c8ffe9` · `by: ai`

**核心。** 朝着错误的方向快速前进，并不是进步。

**例子。** 一个整个项目的文件夹结构在没有通知的情况下被重新组织了。这次改动本身是正确的，但它被完全撤销了，因为另一个人已经基于代码之外的理由决定了那个结构。

**另一个例子。** 有人被要求在两个选项之间做选择：默认关闭一项自动检查，还是保持开启。提问时只说了好处，并且用代码里那项检查的名字来称呼它。对方同意了；改动完成并发布了。之后他们问这样做会有什么坏处，又过了四轮解释，对方才终于能说清关掉了什么。

**检测问题。** 这个改动块是否很大、很难撤销，或者它会改变另一个人已经决定的东西？如果是，就解释并等待。如果不是，就说明你要做什么然后继续：每一步都请求许可，也是有代价的。当我请求同意时，我有没有用对方的话说明可能会出什么问题？

**警示信号。** “我已经知道他们想要什么了。” · “选项 1（推荐）”，却只列出它的好处。

**怎么做。** 在每个大块工作之前，用通俗的语言说明你要做什么、为什么做，然后等待确认。提出选项时，为每个选项写一行，说明它可能出什么问题、撤销起来有多容易；并且用它们做什么来称呼它们，而不是用代码里的名字。如果对方的回答是一个问题，那说明决定还没有做出。

### 35. 顺手记下的待办会过时

`from: 6deec922` · `by: ai`

**核心。** 你在做别的事情时记下的“以后再说”，可能已经不存在了，或者它原本就是一个有意的决定。

**例子。** 一条笔记写着“去掉日期筛选器”。等到真正去做时，这个筛选器已经是团队书面确定的决定了，去掉它会弄坏一份报告。

**检测问题。** 我今天检查过这一项吗，还是只因为它被写下来了，我就去做它？

**警示信号。** “它在待办列表上。”

**怎么做。** 在处理一个待办之前，先在今天检查它，并查找是否有书面决定说明它是被有意保留的。

### 40. 日志记录的是留下了什么、为什么留下，而不是失误的编年史

`from: 8309d6b7` · `by: ai`

**核心。** 变更历史是为了让人理解产品，而不是为了讲述做这次改动的人已经解决的失误。

**例子。** 一份历史写着：“试过 A，失败；试过 B，失败；保留了 C。”几个月后有人读它，他只需要 C 和它的理由，却不得不读完三段才找到它。

**检测问题。** 这一行是帮助人理解产品、避免重蹈覆辙，还是只是记录了发生在我身上的事情？

**警示信号。** “让我们把发生过的每件事都记录下来。”

**怎么做。** 写下最终状态及其理由。试过并失败的内容，只有在它能教会别人某件需要避免重复的事情时，才写进去。

### 47. 并行开展的工作会在共享部分发生冲突

`from: 83287f40` · `by: ai`

**核心。** 多人同时工作时，每个人都能清楚地看到自己负责的那部分。但他们共享的东西（测试、数据、整个项目的文档）会把各自的改动合并在一起：名字相互冲突，副本落后于原件，测试读取了别人尚未完成的工作。集成本身就是工作，不是粘贴。

**例子。** 四个人同时各自写一个部分，但把共享部分当作交付物。集成时，两个交付物使用了共享测试中已经存在的同一个名字，于是那个测试停止运行。另一个测试保留了它所检查内容的一份副本；部分改变了，副本却没有。一次测试运行因为另一个人仍在绘制的图片而失败。最后，每个部分都无法单独保存：共享文件里已经混入了所有人的改动。

**另一个例子。** 两个会话在同一个文件夹里工作，而这个文件夹共享的不只是文件：还有一个被检出的分支、一份构建输出，以及一个测试服务器的端口。一个会话把文件夹切换到了另一个分支；另一个会话的下一次提交落在了那个分支上，而它推送到 main 时却显示“everything up to date”，实际上什么也没有推送。随后把文件夹切回 main，第一个会话尚未提交的改动也一并被带了过来。

**检测问题。** 哪两个部分同时在改同一个文件？谁来集成它？我的测试是否在读取别人尚未完成的工作？在提交之前，这个文件夹当前在哪个分支上？还有谁在用它？

**警示信号。** “我们每个人都测试了自己的部分” · “问题出在另一个部分。” · “我们各自改的文件不同，不会冲突。”

**怎么做。** 由一个人负责集成共享内容，并设置一个步骤，在名字冲突时停止。让测试读取原件，而不是副本。等所有人都完成后运行完整的测试套件，或者在排除仍在变动的部分后运行，并说明被排除的是哪些部分。把共享同一文件的部分一起保存，使每个保存的版本都能完整工作。为每个会话分配它自己的文件夹（`git worktree`），每次提交前读取 `git status -sb`，推送之后检查远程分支上是否已经有这次提交。

### 65. 关于工作方式的规则，对小步骤没有例外

`from: 1f76d0cd` · `by: ai`

**核心。** 关于工作方式的长期指令（谁做什么、在哪里运行、用哪个工具），没有大小之分。“这只是个快速检查”恰恰是这条规则本来要覆盖的情形。

**例子。** 用户曾经要求，并且已经保存在记忆中：所有机械性的工作（安装、运行脚本、转写）都交给更便宜的子智能体模型，主模型只负责推理。给了三个长音频文件之后，主模型自己编写并运行了一次转写样本，“看看里面有什么”；它因为缺少一个库而失败，又重试了一次，直到用户叫停，并指出了这条规则。

**检测问题。** 在一个请求的第一条命令之前：是否存在一条关于谁来做这类步骤、或者怎样做的规则（记忆、项目说明、用户说过的话）？我是不是因为这一步“很小”，就跳过了它？

**警示信号。** “我先快速看一眼，之后再交给别人。” · “这太短了，不值得交给别人做。”

**怎么做。** 按步骤的类型而不是大小来归类：如果它是机械性的，从第一条命令起就按规则所说的方式去做。如果确实有一个例外说得通，就在做之前说明，让用户来决定。
