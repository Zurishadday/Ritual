# 终端与工具

适用于运行命令、服务器、测试或捕获，以及工具介于你和系统之间的情形。

### 27. 先怀疑仪器，再怀疑系统

`from: 82624501` · `by: ai`

**核心。** 如果一个数字该变的时候没有变，或者恰好在你看着它的时候变了，就按以下顺序怀疑：缓存、同时写同一张表的另一个进程、你正在查看的那个工具，最后才是系统本身。

**例子。** 一张表“少了一半的列”。几分钟后它又完整了：你看它的时候，另一个进程正在重建它。

**另一个例子。** 页面上一张新图片“加载不出来”。文件没有问题：测试服务器看不到启动之后才创建的文件夹。一个正在被测量的服务器一直返回旧代码：停止它的任务时，之前的进程仍然占着同一个端口。还有，在已安装插件的两个版本之间运行 `git log` 报错“unknown revision”：本地副本是浅克隆，只有一个提交，历史只存在于远程。

**再一个例子。** 一个脚本“把文本模式算错了”。脚本没有问题：代码经过的那个控制台，在脚本读取之前，把每个 `\n` 都变成了真正的换行。还有在一个笔记本里，各个单元格共享内存，本该出现的错误没有出现：变量还保存着之前某个单元格的值。

**第四个例子。** 一个页面刚部署到预发布服务器上，自动检查就报告有 528 px 的水平溢出以及无障碍警告；几秒钟后，一切都通过了。原因是网站还在提供上一版的样式表。这种情况发生了两次，之后检查改为先等待新文件出现。

**检测问题。** 我看的是系统本身，还是某个缓存、某个副本，或者某个保留了系统旧快照、或在途中改动了它的工具？

**警示信号。** “我已经修过了，可还是一样。” · “这次我确定自己输对了。” · “我刚部署完，现在就可以检查。”

**怎么做。** 在宣布出了大问题之前，过几分钟再取一次快照。如果某个仪器已经用同样的方式让你失望过，就换掉它，而不是继续盯着它：重复出错不是运气不好，而是用错了工具。在途中会改动 `\n` 或 `\\` 的控制台，不适合用来传递代码：代码要写进文件里，用一个不会改动它的工具写入，然后从文件运行。凡是机械性的东西（比如已经失败三次的命令），都要用守卫拦住，而不是靠记忆。在测量服务器之前，先检查哪个进程占着它的端口。在读取某个副本的历史之前，先检查它是不是浅克隆（`git rev-parse --is-shallow-repository`），如果是，就去问远程。部署之后，先在一个循环中等待网站提供一个只有这个版本才有的标记（一个类名、一段文字，或一个 `?v=` 查询参数），并设定尝试次数上限，然后再测量。

### 29. 把命令交给别人之前，先检查一遍

`from: 730b276c` · `by: ai`

**核心。** 替别人运行命令的人是盲目执行的。每个出错的命令，都会消耗他们本可以用来信任下一个命令的那份信任。

**例子。** 一条部署命令里的分支名是凭记忆输入的。那个分支的名字其实不同，执行的人花了半小时才去问。

**另一个例子。** 为了查看某个改动，一个人被交给了 `cd folder && npx next dev -p 3001`。他的终端是 Windows PowerShell 5.1，它不接受 `&&`。修好之后，在他自己的终端里启动，服务器却回应“not found”：要审查的页面只有在设置了一个环境变量之后才会显示，而那条命令并没有设置它。

**检测问题。** 对于这条命令里的每个名字，我是今天从系统里读出来的，还是凭记忆输入的？他们会在哪个 shell、哪个文件夹里运行它？而我是否也是那样运行过它？

**警示信号。** “跟平常的命令一样啊。” · 在给 Windows PowerShell 用的命令里出现 `&&`、`export` 或 `$VAR`。

**怎么做。** 在交给别人之前，自己先运行一遍，并且从系统里复制每个名字（脚本、路径、分支），而不是凭记忆。用他们使用的 shell 来写（在 PowerShell 5.1 里用 `;` 和 `$env:NAME = 'value'`）。在交出一个链接之前，先请求那个确切的地址，确认得到的是你预期的回应。如果是替他们启动服务，就在他们自己的终端里启动，而不是作为你工具调用的子进程（见第 69 条）。

### 44. 你从输出中截掉的部分，可能正是结论

`from: c24ec5bb` · `by: ai`

**核心。** 只看结果的最后几行，或者把它通过另一个命令管道处理，可能会丢掉恰恰写着“失败”的那一部分。一个失败测试的截断输出，看起来和一个通过的测试的输出一模一样。

**例子。** 一个页面被标记为已审查，因为它的测试“执行完毕，没有报错”。结果经过了一个只显示末尾的命令，于是测试失败的提示在途中丢失了。

**另一个例子。** 一个测试套件会自动重试每一个失败的测试。在第二次尝试中通过的测试不计为失败，只被算作“不稳定”，于是原因被隐藏了：每次切换步骤都要向服务器重新请求页面。没有重试时，失败会显现出来，也可以被测量。在另一个套件里，某项检查失败了一次，而重复运行时却通过了：重复运行覆盖了第一次失败的追踪记录，其原因随之丢失。还有一个套件以退出码 0 结束，却没有通过或失败的计数：它的完整输出被保存在测试运行器启动时会清空的文件夹里，于是写出结论的那个工具把它抹掉了。

**再一个例子。** `npm test 2>&1 | tail -4 && git commit …`：一个脚本没有加载成功，测试以错误退出，提交却照样完成了，因为 `&&` 看的是 `tail` 的退出码，而它的退出码总是零。另一种情况是，`Select-Object -First 1` 在脚本输出第一行后就把它截断了，于是脚本没有执行到自己的清理步骤，一个修改过的文件副本因此留了下来。

**检测问题。** 我是在读结论（通过了多少、失败了多少、以什么方式结束），还是只读了输出的一部分？而决定下一步的，是测试的退出码，还是截取命令的退出码？

**警示信号。** “屏幕上没有出现错误” · “最后几行就够了。” · “我把它串在一起，就是一条命令。”

**怎么做。** 在改变状态之前，先找到结论那一行。如果你串联了多条命令，要确保第一条命令的失败能传到最后。如果输出里没有结论，那就表示“我不知道”，而不是“通过了”（见第 1 条）。并且把完整的输出保存到文件里，在文件中查找结论：这样你就不必事先决定要看多少内容。在 shell 里，`set -o pipefail` 会让管道在测试失败时也跟着失败；绝不要中途截断一个会自行清理的脚本。把包含完整输出的文件放在工具启动时会清空的文件夹之外。在重新运行一个失败的测试之前，把第一次失败的追踪记录和截图复制到下一次运行不会触碰的地方。

### 53. 代码应经编辑器修改，而非经 shell 的文本处理

`from: 34503dce` · `by: ai`

**核心。** 用 shell 自带的字符串工具改写源文件（读取、替换、再写回），等于让代码经过为其他用途设计的规则：默认编码、运算符优先级、引号与转义。命令看上去完全正确，文件出来的结果却与命令所表达的不同。

**例子。** 同一次会话中有两次编辑，都发生在 Windows PowerShell 5.1 里。对一个脚本做读取、替换、写回（`Get-Content`、`-replace`、`Set-Content -Encoding utf8`）：它以系统的 ANSI 代码页读入文件，却以 UTF-8 写回，于是其中每个 ✓ 和 · 都变成了 `âœ“` 和 `Â·`，而它的自检也打印出了被弄坏的符号。另一次，用 ``@('old', 'new' + "`n" + 'more')`` 这样的写法列出一组替换项，结果丢掉了几行：在 PowerShell 里逗号的优先级高于 `+`，于是每一对变成了四个元素，而新文本只写入了第一段。

**检测问题。** 这次代码修改是经过编辑器，还是经过 shell 的读取、替换和写回，从而受其编码、优先级和引号规则的支配？

**警示信号。** “这只是个小替换，一条命令就能搞定” · “几处一起替换更快。”

**怎么做。** 用编辑器自带的编辑和写入工具修改代码。如果改动必须用脚本完成，就把脚本写进一个文件，并用能正确读写 UTF-8、字符串字面量朴素直接的解释器运行它（`node fix.mjs`、`python -I fix.py`）。然后检查差异：如果改动的行数超出了你的预期，或者改变了你没有碰过的字符，那就是 shell 的问题。

### 60. 作为进程参数传递的内容有上限，直到它增长时你才会看见

`from: c0be3e59` · `by: ai`

**核心。** 启动另一个程序的库，可能会把你的文本作为命令行参数传给它。操作系统会限制这一行的长度（在 Windows 上约为三万二千个字符），而超出限制时得到的错误，几乎从不提及这一点。

**例子。** 一个服务器通过一个库调用语言模型，该库会启动一个命令行工具，并把一段很长的设置文本作为参数交给它。文本短时一切正常。某个角色的设置文本包含了一份好几页长的规则文件：在 Windows 上它报错“文件名或扩展名太长”，而该库却把它报告为“找不到工具”。修复方法是把这段文本改为通过临时文件传递。

**检测问题。** 这段随内容增长的文本（设置文本、列表、查询）是怎样到达另一个进程的：命令行、环境变量，还是 URL？如果它长十倍，会发生什么？

**警示信号。** “短例子已经能用了。”

**怎么做。** 任何可能增长的内容，都通过文件、标准输入或请求体来传递，绝不作为参数、环境变量或 URL。用你预计的最长文本测试一次，并且在它将运行的最严格的系统上测试。

### 62. 停止后台工作，要先停掉启动它的东西，再证明什么都没有剩下

`from: 9276f71e` · `by: ai`

**核心。** 长时间运行的后台工作通常有一个启动器（一个依次运行各个步骤的脚本）和若干子进程（每个步骤各一个）。只杀掉子进程，启动器就会接着启动下一个步骤；而你报告“已经停止”时，GPU、磁盘或网络仍然在忙。

**例子。** 一位用户要求停止一个整夜运行的模型训练任务。先停止了启动它的智能体，然后停止了正在训练的 Python 进程。随后的检查发现，另一个 Python 进程以新的 PID 在训练：启动器脚本已经转到了下一个步骤。最终需要找出整个进程树，关闭启动器，以及仍在跟随日志的 `tail -f`，并用 `nvidia-smi` 确认 GPU 上还有什么在占用。

**检测问题。** 是谁启动了这个进程？如果我关掉它，它会不会再启动一次？停止之后，用哪条命令可以证明已经没有我的东西在运行？

**警示信号。** “我杀掉了进程，它已经停了。”

**怎么做。** 从启动器开始关闭整个进程树（Windows 上用 `taskkill /t /f`，Unix 上杀掉进程组）。然后按命令行搜索正在运行的进程，查找该任务遗留的任何东西，并检查资源（GPU、端口、文件锁），直到它被释放；只有通过这项检查，才能说“已停止”（见第 38 条）。按设计，让任务有一个干净的停止方式（每个步骤之前都检查一个 `STOP` 文件），并让启动器在某个步骤被杀掉时停止，而不是继续进行下一步。

### 69. 从短命工具里启动的进程，工具一结束就会死掉

`from: 7870a42f` · `by: ai`

**核心。** 从一条会结束的命令（助手的工具调用、CI 步骤、远程会话）里启动的服务器或长时间运行的程序，通常会成为那条命令的子进程。命令结束时，工具或运行器通常会关闭它启动的一切（它的进程组、作业或会话）。你看到它启动并且能够应答；一分钟后它就没了，而且没有任何东西告诉你。

**例子。** 某人本地的应用还在运行旧版本。为了给他换上新版本，有人从助手的命令工具里重新运行了应用的启动脚本，服务器在端口上应答，于是对这个人说：“现在已经是新版本了。”工具调用结束后，系统关掉了它打开的进程，这个人最后连应用都没有了。半小时后，一个智能体发现这些端口上没有任何东西在监听，问题才暴露出来。

**检测问题。** 我刚启动的这个东西，是谁的子进程？当它的父进程结束时，它还会活着吗？我是在工具结束之后检查的，还是只在它运行的时候检查过？

**警示信号。** “我重启了它，它在端口上应答。”

**怎么做。** 人每天都在用的东西，应该由他们自己用自己的快捷方式或服务来启动。如果你必须启动它，就让它脱离父进程（一种在命令结束后仍然存活的后台模式，或系统服务），然后在另一次调用中检查它是否还活着。如果无法保证，就不要说它已经完成：请他们自己打开它。停止这类工作见第 62 条；重复启动见第 22 条。

### 78. 壳层能找到的，程序未必能找到

`from: 8b07c6d7` · `by: ai`

**核心。** 一个命令名在 shell 里能用，但程序启动它时可能失败：shell 会解析一些快捷方式（批处理文件、别名、函数），而直接的系统调用并不认识它们。于是，要么运行的是另一个同名的程序，要么什么也运行不了。

**例子。** 一个 Node 脚本调用 `python` 来生成音频。在 shell 里，`python` 是版本管理器的一个垫片（一个 `.bat` 文件）；而在 Node 里，没有经过 shell，操作系统打开的是一个应用商店的别名，它只会打印“Python was not found”。

**检测问题。** 我在代码里启动的这个程序，是由 shell 解析的（垫片、批处理文件、别名），还是一个真正的可执行文件？我是否从代码里启动它试过，而不只是在 shell 里试？

**警示信号。** “可它在终端里能运行啊。”

**怎么做。** 用启动它的那个程序，把这一步运行一次。如果这个命令是垫片，就通过 shell 来启动它（在 Node 里，Windows 上使用 `shell: true`，参数中不要有空格或引号），或者使用它的完整路径，并让错误信息说明是哪个命令没有找到。另一台机器的情况见第 55 条；另一个脚本的设置，见第 66 条。

### 79. 找不到自己已经做过的东西的生成器，会把所有东西重做一遍

`from: ae59e617` · `by: ai`

**核心。** 一个会跳过已完成工作的进程（靠每个部分的指纹、缓存或工作文件夹），只有在保存着那些状态的机器或检出副本上才是省力的。如果在别处启动，它什么也看不到，就会从头开始：昂贵的工作又要做一遍，而且没有人要求。

**例子。** 一课的旁白是用一个较慢的语音模型逐步录制的（未计时），生成器借助它的工作文件夹跳过未改动的步骤，而这个文件夹不在 git 里。一个代理为了重新生成其中一步，在仓库的另一个检出副本里启动了生成器，那个副本没有这个文件夹：它开始在共享的 GPU 上录制整节课。最后是手动停掉的。

**检测问题。** 让这种跳过的状态保存在哪里？它是否存在于我即将运行的那个文件夹和那台机器上？如果不存在，进程是停下来，还是默默地把所有东西重做一遍？

**警示信号。** “在一个全新的检出副本里，只改了一步。” · 工作文件夹被写进了 .gitignore。 · 一个代理被告知“运行生成器”，却没有被告知它的缓存在哪里。

**怎么做。** 当结果已经存在而状态缺失时，让生成器拒绝从头开始，并说明应当在哪里运行（对于真正想要完整重建的人，提供一个明确的选项，比如 `--all`）。在给代理的任务说明里，写明它运行的文件夹。把状态缺失当成“什么都没做”，就是第 1 条里“我没读到”的另一种形式。

### 82. 一个启动时会清空自己文件夹的工具，会把别人存在那里的东西一并带走

`from: b6b0c760` · `by: ai`

**核心。** 许多工具每次启动都会清空它们的输出文件夹，好让各次运行互不混杂。如果其他进程因为“这是结果文件夹”而把自己的文件也存在那里，下一次运行就会不加警告地把它们删掉，而直到有人去找那个文件时，才会有人发现。

**例子。** 一个浏览器测试运行器每次启动都会清空它的结果文件夹。审查代理把报告存在那里，一个脚本则把每课的步骤文件也存在那里。一天之内，两份长报告丢失了，其中一份是项目负责人要求的；一位审阅者报告其中一个步骤文件不存在，因为几分钟前一次测试运行刚把它删掉了。这些内容后来是从代理的转录记录中恢复的。

**检测问题。** 哪个工具会写入这个文件夹？其中有没有工具会在启动或结束时清空它？我存在这里的东西，能撑过那个工具的下一次运行吗？我是否用一个测试文件验证过？

**警示信号。** “我就放在结果文件夹里好了。” · 对于几分钟前才写入的文件，说“文件不存在”。 · 同一个被忽略的文件夹里，既放着一次性的产物，又放着正式的交付物。

**怎么做。** 给每个会清空文件夹的工具一个它自己的子文件夹（在 Playwright 里是 `outputDir`），把交付物放在它之外，或者放在有版本控制的地方。验证它：放一个测试文件，运行该工具，看它是否还在。把测试的完整输出保存在那个文件夹里，属于第 44 条的情况；编辑由生成器写出的文件，则见第 48 条。

### 83. 从代码启动、输入端保持打开的程序，可能会一直等一个永远不会来的输入

**核心。** 代码启动另一个程序时，如果把它的标准输入留成一个打开的管道，既不写入也不关闭，程序可能会在开始工作前一直等这个输入：几秒，或者永远。不会报错；每次调用只是变慢，而这段时间看起来像是程序自身的启动时间。

**例子。** 一个后台辅助程序每次请求都启动一个命令行助手，标准输入一直保持打开。每次调用要 9 到 22 秒，延迟被归咎于助手的启动。它的错误输出写着它等了 3 s 一个没有到来的输入；忽略输入之后，四次调用的中位数从 22.1 s 降到 12.3 s，两种方式交替测试。

**检测问题。** 我的代码启动程序时，它的标准输入接到了什么：一个我从不写入的打开管道、我的终端，还是什么都没有？我是否读过程序启动时在错误输出里打印了什么？

**警示信号。** “只是启动慢而已” · 每次调用都白白损失同样的几秒。

**怎么做。** 给子进程它需要的输入然后关闭，或者直接忽略（Node 里用 `stdio: ["ignore", "pipe", "pipe"]`，Python 里用 `stdin=subprocess.DEVNULL`，shell 里用 `< /dev/null`）。在测量速度之前先读一次它的错误输出。把启动选项固定在测试里，这样以后的改动就不会再次打开输入。在 shell 里能跑、从代码里失败的命令，属于第 78 条。
