# 界面与设计

适用于人将要看到或使用你所构建的内容的情形：屏幕、组件、样式和页面。

### 10. 成对的模块要一起改

`from: 39a1c52b` · `by: ai`

**核心。** 如果你的产品对两类用户、两个地区或两款产品，各有一个版本的同一屏幕，那么对其中一个的改进，就意味着另一个也有一项待办的改进。

**例子。** 桌面版增加了日期筛选器。而移动版，在用户眼里是“同一个屏幕”，却一个月都没有这个功能。

**检测问题。** 我正在改动的东西，是否有一个用户视为“同一模块”的孪生版本？

**警示信号。** “他们没有在另一个版本上要求我这么做。”

**怎么做。** 在检查过孪生版本并写下“相同”或“不适用，因为……”之前，不要结束这项改动。

### 19. 只审查一个维度，不算审查

`from: e2d5ae25` · `by: ai`

**核心。** “它们已经一样了”，需要你比较了所有你能看到的属性，而不只是其中一个。

**例子。** 两个屏幕的设计为了保持一致，经历了四轮修改：先是尺寸，然后是字体排版，然后是颜色，最后是标签颜色。每次交付都说“完成了”。

**另一个例子。** 一份资料里的插图只审查了内容和尺寸，没有审查对比度：结果有四张图里的两种文字颜色低于最低可读水平。

**检测问题。** 我比较的是一个属性，还是用户能看到的所有属性？

**警示信号。** “尺寸现在一样了，所以设计是一样的。”

**怎么做。** 在修复第一个差异之前，先列出所有差异。在你的记录中，动词会暴露你：“修好了”和“会变成”是意图；“它显示”和“它呈现”才是测量。

### 31. 屏幕上不放技术性内容，除非它会改变一个决定

`from: 60f4261e` · `by: ai`

**核心。** 业务屏幕上的每个元素都应该有助于做出某个决定。方便审计的内容放在代码里；方便决策的内容放在屏幕上，并使用业务语言。

**例子。** 一个销售屏幕在第一行显示了每个订单的内部 ID，以及上次计算的时间。没有人靠它们做任何决定，它们却占据了真正重要的数据的位置。

**检测问题。** 这会改变使用这个屏幕的人的任何决定吗？如果不会，它为什么在这里？

**警示信号。** “万一有人需要呢。”

**怎么做。** 在往屏幕上添加任何东西之前，先写下它会改变什么决定。如果它什么都不改变，就放到技术日志或代码里，而不是屏幕上。

### 32. 能用但看不见的东西，会被报告为坏了

`from: 62e8051c` · `by: ai`

**核心。** 如果一个按钮改变的东西在用户的视野之外，那么对用户来说，有效和无效看起来是一样的。

**例子。** 一个筛选器确实筛选了表格，但表格在两屏之外的地方。他们却报告说它“没有任何作用”。

**变体。** 隐藏一个容器，会把里面的所有东西都隐藏掉，即使有些东西和它毫无关系。例如，一个有用的链接恰好位于一个已废弃的控件里面。

**检测问题。** 使用完这个控件后，不挪动位置，用户能看到发生了什么变化吗？

**警示信号。** “它确实有用，只是看不出来。”

**怎么做。** 每个控件都要说明它改变了什么，并把用户带到那个地方。在隐藏任何东西之前，先检查里面还有哪些其他元素。

### 33. 字形不等于文字

`from: ba84572f` · `by: ai`

**核心。** 在小字号下，“÷”和“+”、“l”和“1”、“O”和“0”很容易被混淆。如果两个人都把同一段文字读错了，那不是他们分心，而是字号的问题。

**例子。** 两个不同的人在一张小字号的卡片上，都把“98 ÷ 441”读成了“98 + 441”，并且都报告说这个计算是错的。

**另一个例子。** 一份资料的代码字体把 `>=` 连写成了一个符号 ⩾。学习者照着所见抄写，而这个符号既不在键盘上，也不在语言中存在。

**检测问题。** 在它将被阅读的字号和字体下，这个符号会不会和另一个符号混淆？或者它看起来像一个无法键入的东西？

**警示信号。** “在我的屏幕上看起来没问题。”

**怎么做。** 当一个符号容易混淆时，用文字替换它：用“98 除以 441”代替“98 ÷ 441”。

### 41. 要以读者真正看到的形式来检查

`from: d5bc89cb` · `by: ai`

**核心。** 在文本中找到某个词，并不能证明它会显示出来。文本可能在文档的其他地方，而应该负责显示它的格式却输出为空。

**例子。** 三个编号步骤显示成了空的项目符号。自动检查通过了，因为这些词在文档的别处出现过。

**另一个例子。** 添加了一条“右侧还有更多列”的提示，因为代码已经写好，就被当作完成了。它却从未出现过：一条通用的表格样式移除了触发它的条件。后来是别人在截图中看到的。

**再一个例子。** 一个答案选项在文件中写着“总计：{2 * 78}”。页面绘制时，系统计算了花括号里的内容，显示为“总计：156”：于是出现了两个完全相同的选项。只有看屏幕的人才发现了这一点。

**检测问题。** 我是否以读者看到的方式看到了那个确切的元素，还是只是在源文件中找到了那个词（或那段代码）？

**警示信号。** “这个词在文件里” · “这只是一行的修复。”

**怎么做。** 检查确切的元素，比如“这三个步骤，以项目符号显示”，并且至少有一次以读者将看到的方式查看页面。即使是小修复也要检查：因为那里最可能被另一条规则覆盖。第一次在页面上使用新资源（代码块、固定页眉）时，也要在手机上看一眼。

### 45. 也会有人走进错误的路径

`from: 93409a9c` · `by: ai`

**核心。** 如果你只测试一切顺利时会发生什么，那么犯错的人就会找到这个漏洞。而在学习时，犯错是最常见的事情。

**例子。** 一个查询单元格只有在查询运行时才计为一次尝试。输入有拼写错误时，前进按钮永远不会激活，使用者就卡住了。测试都通过了，因为它们总是运行那条没有错误的起始查询。

**检测问题。** 如果用户做了最可能的错误操作（拼写错误、空答案、连点两次），他们会看到什么？他们还能继续吗？

**警示信号。** “答对了它就能用。”

**怎么做。** 对每个控件，测试三条路径：正确的路径、最常见的错误和空的情况。三者都要说明发生了什么，并让用户能继续下去。

### 46. 每次请求都要运行的东西，不能随内容一起增长

`from: b7ad7ec2` · `by: ai`

**核心。** 在每个页面上都要做的事情，比如读取全部内容或重新计算索引，在十个页面时成本很低，在一百个页面时就很高。它是逐渐增长的，没有人会注意到，直到某些东西开始“时不时”出错。

**例子。** 网站的每个页面都会读取并解析全部内容，以生成目录。单独一个页面只需 0.4 秒。但侧边栏一次请求大约 40 个页面，加在一起就要 16 秒。几个月后，测试开始在切换页面时失败，而失败的样子看起来像是测试本身的问题。

**检测问题。** 这个每次请求都运行的东西，是否要遍历全部内容？它今天需要多长时间，内容翻倍后需要多长，以及很多请求同时到达时需要多长？

**警示信号。** “在本地加载得很快” · “这是一个间歇性的失败。”

**怎么做。** 在编译后的服务器上，并以人们实际使用的方式，把所有请求放在一起测量，而不是只测一个页面。缓存服务器运行期间不会改变的内容；并留下一个测试，用真正导致变慢的那种情况去测量它。

### 49. 通用规则不能悄悄压过具体规则

`from: 4a81cf45` · `by: ai`

**核心。** 一条适用于所有东西的规则（全局样式、默认值），可以在没有任何警告的情况下，覆盖每个部件自己做出的决定。

**例子。** 为整个网站编写的键盘焦点样式，自带了一个圆角。由于它的优先级高于每个组件自己的样式，一个药丸形状的按钮在用键盘获得焦点时，形状就变了。没有人注意到，因为用鼠标时焦点根本不会出现。

**检测问题。** 这条通用规则是否触及了每个部件自己已经决定的东西？如果它们相互冲突，哪一个会获胜？

**警示信号。** “我把它做成全局的，这样就不用重复写了。”

**怎么做。** 让通用规则只触及它自己负责的东西（焦点轮廓，而不是形状）。如果它应该有意获胜，就在它旁边写下来。并且要在最不同的那个部件上测试，而不只是最常见的那个。

### WEB-2. 公开的表单从第一天起就会遇到机器人

`from: 6a05ed7d` · `by: ai`

**核心。** 一个对互联网开放的表单，不会只被真人填写。如果没有任何东西阻止自动提交，而且阅读消息的人也无法清理这些垃圾信息，那么第一波垃圾就会淹没真正的客户。

**例子。** 在 Web 模拟的两次运行中，联系表单都在几秒钟之内接收了脚本发来的 650 条消息，全都写着“谢谢”。管理员没有分页，也没有删除按钮：管理页面增长到一百万到六百万像素那么高，而在手机上，消息的文字会超出屏幕。两次都被构建者记为待办。

**检测问题。** 如果明天到达一千条假消息，主人怎么找到那一条真实的消息，又如何删除其余的？

**警示信号。** “这是个小站点，不会有人攻击它的” · “以后再加限制吧。”

**怎么做。** 从一开始就设置一个低成本的制动装置：一个人不会去填的隐藏字段，以及每个地址每分钟的提交次数限制。还要有一个管理后台，支持分页、最新的排在最前，并能删除或标记为垃圾。测试方法是：用脚本发送数百条消息，然后在手机上打开管理后台。

### WEB-3. 没有人测试过的备用方案，不算备用方案

`from: c0e4cb66` · `by: ai`

**核心。** 带有 `method` 和 `action` 的表单承诺一种备用方案，即使 JavaScript 失效也能工作。但如果服务器只响应 JavaScript 期待的请求，这个承诺就是假的，而用户最后面对的只是一堆代码。

**例子。** 在 Web 模拟的两次运行中，表单都通过 JavaScript 提交，并声明了 `method="post"`。在没有 JavaScript 的情况下，一个版本的服务器返回一行 JSON 拒绝了提交，消息就丢失了；另一个版本保存了消息，却只在一个空白页面上显示 `{"ok":true}`。第二个版本的总结说，它不会在没有 JavaScript 的情况下提交。

**检测问题。** 如果这个 JavaScript 文件没有加载，用户提交时会看到什么？

**警示信号。** “反正大家都有 JavaScript” · “我把 `action` 留着，以防万一。”

**怎么做。** 在两者中选定一个并测试：要么服务器接受普通提交，并返回一个页面（或重定向到感谢页面），要么表单不声明它并不具备的备用方案。关闭 JavaScript 后提交一次。

### WEB-4. 禁用按钮时，焦点也会跟着消失

`from: 4dc9e2b6` · `by: ai`

**核心。** 在提交时禁用按钮可以防止重复提交，但按钮会失去焦点，浏览器会把焦点移到文档上。使用键盘的人在看到提示后，只能从头开始。

**例子。** 在 Web 模拟的两次运行中，提交时都禁用了按钮。服务器拒绝了一个邮箱后，提示出现在按钮下方，焦点落在了文档上，于是下一次 Tab 把用户带到了页面上的第一个链接，远离了需要修改的那个字段。

**检测问题。** 提交之后，无论成功还是失败，焦点落在哪里？下一次按 Tab 会去哪里？

**警示信号。** “我禁用它，这样就没人能重复提交。”

**怎么做。** 提交完成时，把焦点放在用户需要继续的地方：出错的字段（用 `aria-invalid` 标记，并在旁边显示其提示信息），或者成功提示上。或者，使用 `aria-disabled` 和一个标志位来防止重复提交，而不是禁用按钮。只用键盘走一遍错误流程。

### WEB-5. 没有尝试次数限制的密码登录，安全性只取决于最弱的那个密码

`from: 0e974320` · `by: ai`

**核心。** 对每个错误密码都以全速作答的登录，任何人每分钟都能试上千次。强大的默认密码会掩盖这个问题，直到所有者设置了自己的密码；而没有任何机制阻止这个密码过短。

**例子。** 在 Web 模拟重跑的两次运行中，管理页面要求输入密码，却从不限制失败的尝试次数：连续 200 次错误密码，得到了 200 次拒绝，用时不到一秒，没有任何一次被拦截。默认密码又长又随机，但构建者自己的总结告诉所有者如何设置新密码，却没有要求它必须够长。

**检测问题。** 在一分钟内，有人能对这个登录尝试多少次错误密码？第五次之后会发生什么？

**警示信号。** “默认密码很强。” · “这只是管理页面而已。”

**怎么做。** 对重复的失败进行减速或封锁，按来源地址和按账户分别计算，并让等待时间逐次增长。所有者设置密码时，要求最小长度。测试方法：连续发送二十个错误密码，检查最后几次是否被拦截。
