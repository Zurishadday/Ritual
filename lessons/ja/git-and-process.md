# Git とプロセス

保存、終了、引き継ぎ、調整をするときに当てはまること：コミット、状態、保留項目、並行作業。

### 8. 利用先は記憶せず、書き出して一覧にする

`from: b3d4e214` · `by: ai`

**要点。** 他の人が名前で読んでいるデータを変えるとき、それを読んでいる人の一覧を書き留めておかなければならない。記憶は必ず一つ漏らす。

**例。** あるモデルが変わった後、三つの画面のラベルを更新した。記憶になかった四つ目の画面は、前のモデルの選択肢を出し続けた。

**別の例。** 章を書くとき、読者は前の章の三つの関数をすでに知っていると、記憶から書いた。検索すると、その章では一つしか教えていないことが分かった。また、新しいものとして扱った話題は、別の章ですでに説明されていた。

**もう一つの例。** 変更は、記憶から書いたファイルの一覧とともに保存されたが、一つ漏れていた。新しいものを動かすために必要だったファイルである。後で確認した保留中の変更の一覧が、それを示した。

**検出の問い。** この利用者の一覧は、どこから得たか？ 検索か、それとも記憶か？

**危険信号。** 「使われている三か所はもうカバーした」「それはもう見てもらっている」「必要なものはすべて追加した」

**どうするか。** 変更の種類ごとに、影響の対応表を書き留めておく。それを最後まで見て、「変更する」か「〜のため該当しない」と言う。そして変更によって新しい利用先が生まれるなら、同じ変更の中で追加する。出典を引用する前には、その出典から、自分が主張している文をコピーする。誰かが別の人のしたこと、見たことを語るときも、確認が必要である。

### 9. 一つの状態は複数の記録に存在する。一緒に動かす

`from: bc14d730` · `by: ai`

**要点。** 保留中の項目を閉じるには、通常三か所が関わる。保留項目の一覧、それを監視するテスト、それを説明する文書である。一つだけ動かすと、残りは矛盾する。

**例。** 保留項目は一覧では閉じたことになっていたが、それを監視するテストは「失敗が想定される」のままで、文書にはまだ未解決と書かれていた。三か所、三つの版。

**検出の問い。** この状態を主張している他の場所はどこか？ 保存する前に名前を挙げる。

**危険信号。** 「後で反対側も更新しよう」

**どうするか。** 作業の単位は、同じ変更の中で行う、完全な一式である。

### 30. 動く前に説明し、承認を待つ

`from: a2c8ffe9` · `by: ai`

**要点。** 間違った方向に速く動くことは、前進ではない。

**例。** プロジェクト全体のフォルダ構成が、知らせもなく再編された。その変更はそれ自体は正しかったが、完全に元に戻された。別の人が、コードには書かれていない理由で、その構成をすでに決めていたからである。

**別の例。** ある人に、自動チェックを既定でオフにするか、オンのままにするかを選んでもらった。質問は利点だけを示し、そのチェックをコード上の名前で呼んでいた。その人は「はい」と答え、作業は行われて公開された。その後、それで何が損なわれるのかを尋ねた。何がオフにされたのかを、その人が言えるようになるまでに、さらに四回の説明が続いた。

**検出の問い。** このブロックは大きいか、元に戻しにくいか、あるいは別の人がすでに決めたことを変えるか？ そうなら、説明して待つ。そうでなければ、何をするかを言って進める。どのステップでも許可を求めることにも、コストがかかるからである。承認を求めるとき、私は相手の言葉で、何がうまくいかないかを言ったか？

**危険信号。** 「相手が何を望んでいるかは、もう分かっている」「「選択肢 1（推奨）」と書いて、利点だけを並べる」

**どうするか。** 作業の大きなブロックを始める前に、何をするか、なぜかを平易な言葉で説明し、確認を待つ。 選択肢を出すときは、それぞれについて、何がうまくいかないかと、どれくらい簡単に元に戻せるかを一行ずつ書く。また、ものの名前は、コード上の名前ではなく、それが何をするかで呼ぶ。相手の答えが質問なら、まだ決定はされていない。

### 35. 途中で書き留めた「あとでやること」は古くなる

`from: 6deec922` · `by: ai`

**要点。** 別のことをしている最中に「後で」と書き留めたものは、もう存在しないかもしれないし、意図的な決定だったかもしれない。

**例。** メモには「日付フィルターを削除する」とあった。ようやく取りかかったとき、そのフィルターはチームが書面で決めたことになっており、削除するとレポートが壊れた。

**検出の問い。** この項目を今日確認したか、それとも、書かれているからといって取りかかろうとしているのか？

**危険信号。** 「リストに入っていた」

**どうするか。** 保留中の項目に取りかかる前に、今日それを確認し、そのままにしたのが意図的だったと示す、書面の決定を探す。

### 40. 記録は、何が残り、なぜかを書く。失敗の年代記ではない

`from: 8309d6b7` · `by: ai`

**要点。** 変更の履歴は、製品を理解するためのものであって、変更した人が解決済みの失敗を語るためのものではない。

**例。** 履歴には「A は試して失敗、B は試して失敗、C を残した」とあった。数か月後にそれを読む人が必要としたのは C とその理由だけだったが、見つけるには三段落を読まなければならなかった。

**検出の問い。** この行は、製品を理解したり、同じ失敗を繰り返さないことを助けたりするか？ それとも、ただ自分に起きたことを記録しているだけか？

**危険信号。** 「起きたことは全部記録しておこう」

**どうするか。** 最終的な状態とその理由を書く。試して失敗したことは、同じ失敗を繰り返さないために誰かが必要とするものを教える場合にだけ書く。

### 47. 並行作業は、共有されたものの中で衝突する

`from: 3565a1b4` · `by: ai`

**要点。** 複数の人が同時に作業すると、各自は自分の部分をはっきり見ている。しかし、共有されるもの（テスト、データ、プロジェクト全体の文書）では、変更が合流してしまう。名前が衝突し、コピーが遅れ、他の人の未完成の作業を読むテストが生まれる。統合は、貼り付けではなく作業である。

**例。** 四人がそれぞれ同時に一つの部分を書き、共有の部分を成果物として残していた。統合のとき、二つの成果物が、共有テストにすでにある名前を使っていたため、そのテストは走らなくなった。別のテストは、自分が確認するものの写しを持っていた。部分は変わったが、写しは変わらなかった。あるテストの実行は、別の人がまだ描いていた画像のせいで失敗した。そして最後には、各部分を単独で保存することができなくなった。共有ファイルには、すでに全員の変更が入っていたからである。

**検出の問い。** 二つの部分が同時に触れているファイルはどれか。そして誰がそれを統合するのか？ 私のテストは、他の人の未完成の作業を読んでいないか？

**危険信号。** 「それぞれ自分の部分はテストした」「失敗は別の部分にある」

**どうするか。** 共有されるものは一人が統合する。名前が衝突したら止まるステップを入れる。テストは写しではなく、元のものを読むようにする。全員が終わったら、あるいは変更中の部分を除いて、テストスイート全体を一度実行する。そして除外した部分を言う。同じファイルを共有する部分は一緒に保存し、保存されたそれぞれのバージョンが全体として動くようにする。
