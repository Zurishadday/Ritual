# コンソールとツール

コマンド、サーバー、テスト、キャプチャを実行するときや、ツールが自分とシステムの間に入るときに当てはまること。

### 27. システムを疑う前に、計器を疑う

`from: 11b6d719` · `by: ai`

**要点。** 数字が変わるべき時に変わらなかったり、見ている最中にちょうど変わったりしたら、次の順に疑う。キャッシュ、同じテーブルに書き込んでいる別のプロセス、見ているツール、そして最後の最後にシステムそのもの。

**例。** テーブルの列が「半分消えた」。数分後には完全になっていた。見ていたとき、別のプロセスがそれを再構築していたのである。

**別の例。** 新しい画像がページで「読み込まれない」。ファイルは問題なかった。テストサーバーは、起動後に作られたフォルダを見ることができなかったのである。計測中のサーバーは、古いコードで応答し続けていた。タスクを止めたときに、前のプロセスが同じポートで生きたままになっていたのである。また、インストール済みプラグインの二つのバージョンの間で `git log` を実行すると、「unknown revision」で失敗した。ローカルのコピーは浅いクローンで、コミットは一つしか持っておらず、履歴はリモートにしかなかったのである。

**もう一つの例。** あるスクリプトが「テキストパターンを間違って計算した」。スクリプトは問題なかった。コードを渡すコンソールが、スクリプトが読む前に、すべての `\n` を実際の改行に変えていたのである。そして、セルが記憶を共有するノートブックでは、本来表示されるべきエラーが表示されなかった。変数が、以前のセルで保存されたまま残っていたからである。

**検出の問い。** 私は今、システムを見ているのか、それとも、システムの古いスナップショットを保持していたり、途中で変えてしまったりするキャッシュ、コピー、ツールを見ているのか？

**危険信号。** 「もう直したのに、まだ同じだ」「今度こそ、ちゃんと打ち間違えずに入力した」

**どうするか。** 大惨事だと宣言する前に、数分後にもう一度スナップショットを取る。計器がすでに同じように失敗させたことがあるなら、それを見続けるのではなく取り替える。繰り返される失敗は運の悪さではなく、間違ったツールである。途中で `\n` や `\\` を変えてしまうコンソールは、コードを渡すには向かない。コードはファイルに書き、それに触らないツールで書き、そこから実行する。そして機械的なもの（三回すでに失敗したコマンド）は、覚えておくのではなく、ガードでブロックする。サーバーを計測する前に、どのプロセスがそのポートを保持しているかを確かめる。コピーの履歴を読む前に、それが浅いクローンかどうかを確かめ（`git rev-parse --is-shallow-repository`）、そうであればリモートに尋ねる。

### 29. 誰かに渡す前に、コマンドを確認する

`from: 0c95aa16` · `by: ai`

**要点。** 誰かの書いたコマンドを実行する人は、目隠しをして実行している。壊れたコマンドは、一つ壊れるたびに、次のコマンドに対する信頼を消費してしまう。

**例。** デプロイのコマンドには、ブランチ名が記憶から打ち込まれていた。ブランチは別の名前になっていた。実行した人は、質問する前に三十分を失った。

**検出の問い。** このコマンドの各名前を、今日、システムから読んだか、それとも記憶から打ち込んだか？

**危険信号。** 「いつもと同じコマンドだ」

**どうするか。** 人に渡す前に、自分で実行する。そして各名前（スクリプト、パス、ブランチ）は、記憶からではなく、システムからコピーする。

### 44. 出力から切り捨てたものが、判定であることがある

`from: c24ec5bb` · `by: ai`

**要点。** 結果の最後の数行だけを見たり、別のコマンドに通したりすると、まさに「失敗した」と言っていた部分が捨てられてしまうことがある。失敗したテストの切り詰められた出力は、通ったテストの出力とまったく同じに見える。

**例。** あるページは、テストが「エラーなく終わった」ので、レビュー済みとされた。結果は末尾しか表示しないコマンドに通され、テストが失敗したという通知は途中で消えていた。

**別の例。** あるテストスイートは、失敗したテストを自動的に再試行していた。二回目で通ったテストは、失敗ではなく「不安定」として数えられ、原因は隠れたままだった。ステップが変わるたびに、サーバーにページを再度要求していたのである。再試行をやめると、失敗が現れ、測定できるようになった。別のテストスイートでは、あるチェックが一度失敗し、繰り返したときに通った。繰り返しが最初の失敗のトレースを上書きしてしまい、その原因は失われた。また、あるテストスイートは、終了コード 0 で、合格も不合格も数えられずに終わった。その完全な出力は、テストランナーが起動時に空にするフォルダの中に保存されていたため、判定を書くツールがそれを消してしまっていたのである。

**もう一つの例。** `npm test 2>&1 | tail -4 && git commit …` では、スクリプトが読み込めず、テストはエラーで終了したが、コミットは通ってしまった。`&&` が見ていたのは `tail` の終了コードで、それは常にゼロだからである。別の場合では、最初の一行が出た時点で `Select-Object -First 1` がスクリプトを打ち切った。そのためスクリプトは自分の後始末まで届かず、ファイルの変更されたコピーが残った。

**検出の問い。** 私は判定（何件通り、何件失敗し、どう終わったか）を読んでいるのか、それとも出力の一部だけを読んでいるのか？ そして、次に何をするかを決めるのは、テストの終了コードか、それとも切り詰めるコマンドの終了コードか？

**危険信号。**「画面にエラーは出なかった」「最後の数行で十分だ」「一行につないであるので、一つのコマンドだ」

**どうするか。** ステータスを変える前に、判定の行を探す。コマンドをつなぐなら、最初のコマンドの失敗が最後まで届くようにする。出力に判定がなければ、それは「分からない」を意味し、「通った」ではない（教訓 1 を参照）。そして、出力全体をファイルに保存し、判定をそこで探す。そうすれば、どこまで読むかを事前に決めなくて済む。 シェルでは、`set -o pipefail` を使うと、テストが失敗したときにパイプも失敗する。自分で後始末をするスクリプトは、途中で打ち切ってはならない。出力全体を入れたファイルは、ツールが起動時に空にするフォルダの外に保管する。失敗したテストをもう一度実行する前に、最初の失敗のトレースとスクリーンショットを、次の実行が触れない場所にコピーする。

### 53. コードはシェルの文字列処理ではなく、エディタを通す

`from: 34503dce` · `by: ai`

**要点。** シェル自身の文字列ツールでソースファイルを書き直す（読み込み、置換、書き戻し）と、コードは別の目的のために作られた規則を通ってしまう。既定の文字コード、演算子の優先順位、引用符とエスケープである。変更はコマンドの中では正しく見えるが、ファイルは、コマンドが言っているように見えるものとは違う形で出来上がる。

**例。** 一つのセッションでの二つの編集で、どちらも Windows PowerShell 5.1 でのものだった。スクリプトを読み込み、置換し、書き戻す処理（`Get-Content`、`-replace`、`Set-Content -Encoding utf8`）は、ファイルをシステムの ANSI コードページで読み、UTF-8 で書き戻した。そのため、中にあった ✓ と · はすべて `âœ“` と `Â·` に変わり、スクリプトの自己チェックは崩れた記号を表示した。次に、置換の一覧を ``@('old', 'new' + "`n" + 'more')`` と書いたところ、行が抜け落ちた。PowerShell では、カンマが `+` より強く結びつくため、各ペアが四つの要素になり、新しいテキストのうち最初の部分だけが書き込まれたのである。

**検出の問い。** このコードの変更は、エディタを通っているか。それとも、シェルの読み込み、置換、書き込みを通り、その文字コード、優先順位、引用符の規則を受けているか？

**危険信号。**「ちょっと置換するだけだから、一つのコマンドでやってしまおう」「置換をまとめてやった方が速い」

**どうするか。** コードは、エディタ自身の編集と書き込みの機能で変える。変更をスクリプトで行う必要があるときは、スクリプトをファイルに書き、UTF-8 を読み書きし、文字列リテラルが素直なインタープリターで実行する（`node fix.mjs`、`python -I fix.py`）。そのうえで差分を見る。意図したより多くの行に触れた変更、あるいは触れるつもりのなかった文字が変わった変更は、シェルの仕業である。

### 60. プロセスの引数として渡すものには、大きくなるまで見えない上限がある

`from: c0be3e59` · `by: ai`

**要点。** 別のプログラムを起動するライブラリは、テキストをコマンドライン引数としてそのプログラムに渡すことがある。オペレーティングシステムはその行の長さに上限を設けており（Windows では約3万2千文字）、その上限を越えたときに出るエラーは、ほとんどそのことを教えてくれない。

**例。** サーバーは、長いセットアップテキストをフラグとして渡すライブラリを通じて、言語モデルを呼び出していた。短いテキストでは動いていた。ある役割のセットアップテキストには、数ページにわたるルールファイルが含まれていた。Windows では「the filename or extension is too long」と失敗し、ライブラリはそれを「tool not found」と報告した。そのテキストを一時ファイルで渡すことで直った。

**検出の問い。** 内容とともに大きくなるこのテキスト（セットアップテキスト、リスト、クエリ）は、どうやって別のプロセスに届くか。コマンドライン、環境変数、URL のどれか？ それが十倍長くなったら、何が起こるか？

**危険信号。**「短い例では、もう動いていた」

**どうするか。** 大きくなりうるものは、必ずファイルで運ぶ。標準入力を通すか、リクエストの本体に入れる。引数、環境変数、URL として運んではならない。予想される最も長いテキストで、一度テストする。それが動く中で最も厳しいシステムで。

### 62. バックグラウンド作業を止めるには、それを起動しているものを止め、何も残っていないことを確かめる

`from: 9276f71e` · `by: ai`

**要点。** 長く動くバックグラウンド作業には、たいてい起動元（ステップを順に実行するスクリプト）と、子プロセス（各ステップ）がある。子プロセスだけを止めると、起動元が次のステップを始めてしまう。そのあいだ GPU、ディスク、ネットワークは忙しいままなのに、あなたは「止まった」と報告している。

**例。** ユーザーは、一晩中動いていたモデル学習のジョブを止めるよう頼んだ。まず、それを起動したエージェントを止め、次に学習中の Python プロセスを止めた。その後の確認で、新しい PID で学習している別の Python プロセスが見つかった。起動元のスクリプトが、すでに次のステップに移っていたのである。プロセスのツリー全体を見つけ、起動元を閉じ、ログを追いかけ続けている `tail -f` も閉じ、そして `nvidia-smi` で、GPU をまだ何が使っているかを確かめる必要があった。

**検出の問い。** このプロセスを起動したのは誰か。それを閉じたら、起動元はまたそれを起動するか。止めた後、自分のものがまだ何も動いていないことを示すコマンドは何か？

**危険信号。**「プロセスを殺したから、止まった」

**どうするか。** 起動元から、ツリー全体を閉じる（Windows では `taskkill /t /f`、Unix ではプロセスグループを kill する）。そのうえで、そのジョブから残ったものが実行中のプロセスにないか、コマンドラインで探す。そして、リソース（GPU、ポート、ファイルロック）が空くまで確かめる。その確認の後で初めて「止まった」と言う（教訓 38 を参照）。さらに、設計として、ジョブにきれいな停止手段を持たせる（各ステップの前に確認する `STOP` ファイル）。そして、子プロセスが kill されたら、起動元は次のステップに進まず、止まるようにする。
