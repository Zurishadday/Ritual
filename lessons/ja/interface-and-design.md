# インターフェースとデザイン

人が見たり使ったりするものを作るときに当てはまること：画面、コンポーネント、スタイル、ページ。

### 10. 双子のモジュールは、一緒に変わる

`from: 39a1c52b` · `by: ai`

**要点。** 同じ画面の二つの版を、二種類のユーザー、二つの地域、二つの製品のために持っているなら、一方への改善は、もう一方への保留中の改善である。

**例。** デスクトップ版に日付フィルターが追加された。ユーザーが「同じ画面」だと思っているモバイル版には、一か月間それがなかった。

**検出の問い。** 私が触っているものには、ユーザーが「同じモジュール」だと見なす双子がいるか？

**危険信号。** 「向こうはそれを頼まれていない」

**どうするか。** 双子を確認し、「同じ」か「〜のため該当しない」のどちらかを書くまで、変更を終えない。

### 19. 一つの次元だけのレビューは、レビューではない

`from: e2d5ae25` · `by: ai`

**要点。**「もう同じになっている」と言うには、見えるすべての性質を比べていなければならない。一つだけではだめである。

**例。** 二つの画面のデザインを、四回のラウンドを経て揃えた。最初はサイズ、次は書体、次は色、最後はラベルの色。各納品で「完了した」と言われた。

**別の例。** ある資料のイラストは、内容とサイズはレビューされたが、コントラストはレビューされていなかった。その結果、二つの文字色が、四枚の画像で、最低限読めるレベルを下回っていた。

**検出の問い。** 一つの性質を比べたのか、それとも、ユーザーが見るすべての性質を比べたのか？

**危険信号。** 「サイズが合っているから、デザインは同じだ」

**どうするか。** 最初の違いを直す前に、すべての違いを挙げる。そして、メモの動詞がそれを明かす。「直った」「〜になる」は意図であり、「〜と書いてある」「〜と表示される」は測定である。

### 31. 意思決定を変えないかぎり、画面に技術的なものは載せない

`from: 60f4261e` · `by: ai`

**要点。** 業務画面のすべての要素は、何かを決める助けになるべきである。監査を助けるものはコードに入れる。決める助けになるものは、業務の言葉で画面に載せる。

**例。** 販売画面は、最初の行に各注文の内部 ID と、最後に計算された時刻を表示していた。誰もそれで何かを決めていなかったが、本当に重要なデータのスペースを奪っていた。

**検出の問い。** この変更は、画面を使う人の決定を変えるか？ 変えないなら、なぜここにあるのか？

**危険信号。** 「念のため」

**どうするか。** 画面に何かを加える前に、それがどの決定を変えるかを書き出す。どれも変えないなら、画面ではなく、技術ログかコードに入れる。

### 32. 動いているのに見えないものは、壊れていると報告される

`from: 62e8051c` · `by: ai`

**要点。** ボタンが、表示の外にあるものを変えるなら、ユーザーにとって、動いている場合と動いていない場合の見え方は同じである。

**例。** フィルターはテーブルを確かに絞り込んでいたが、テーブルは二画面分下にあった。人々はそれを「何もしない」と報告した。

**変形。** 何かを隠すと、その中にあるものもすべて隠れる。それが無関係なものであっても。例えば、廃止されたコントロールの中にあった、役に立つリンクなど。

**検出の問い。** コントロールを使った直後、その場所から動かずに、ユーザーは何が変わったかを見られるか？

**危険信号。** 「ちゃんと動いてはいる。ただ表示されないだけだ」

**どうするか。** すべてのコントロールは、何が変わったかを伝え、ユーザーをそこへ連れて行く。そして何かを隠す前に、その中にどんな要素があるかを確認する。

### 33. 字形は文字ではない

`from: ba84572f` · `by: ai`

**要点。** 小さな活字では、「÷」と「+」、「l」と「1」、「O」と「0」が混同される。二人が同じものを誤って読むなら、それは気が散っているからではなく、活字の大きさのせいである。

**例。** 二人の別々の人が、小さな活字のカードにある「98 ÷ 441」を「98 + 441」と読み、二人とも計算が間違っていると報告した。

**別の例。** 教材のコードフォントは、`>=` を一つの記号 ⩾ につないでしまっていた。学習者は見たものをそのままコピーするが、その記号はキーボードにも言語にも存在しない。

**検出の問い。** 読まれる大きさとフォントで、この記号は別のものと混同されうるか、それとも、入力できないものに見えるか？

**危険信号。** 「私の画面では問題なく見える」

**どうするか。** 記号が混同されるなら、言葉に置き換える。「98 ÷ 441」の代わりに「98 割る 441」と書く。

### 41. 読み手が実際に見る形式で確認する

`from: 10a08b3c` · `by: ai`


**要点。** テキストの中に単語があることを確かめても、それが表示されることは証明されない。テキストは文書の別の場所にあって、表示されるはずの形式が空のまま出てくることがある。

**例。** 番号付きの三つの手順が、空の箇条書きとして出てきた。その単語は文書の別の場所に存在していたため、自動チェックは通ってしまった。

**別の例。** 「右にまだ列があります」という表示が追加され、コードがあるので完了とされた。しかし一度も表示されなかった。テーブルの一般的なスタイルが、それを有効にする条件を取り除いていたのである。別の人がスクリーンショットでそれに気づいた。

**もう一つの例。** ある回答の選択肢は、ファイルの中では「合計: {2 * 78}」だった。ページが描画されると、システムは中括弧の中身を計算し、「合計: 156」と表示した。二つの同じ選択肢になってしまった。画面を見た人だけがそれに気づいた。

**変形。** レビューする人が判断するスクリーンショットは、誰も到達しない画面を映すことがある。あるコースの撮影ツールは、コードの練習に対して、先へ進むための埋め草の行を返していたので、「実行後」のスクリーンショットには、その行と「期待される結果ではありません」というメッセージが映っていた。レビューする人は、正解した学習者が見るものを一度も見ていなかった。デスクトップでは、撮影にヘッダーとサイドメニューも入り、レッスンは読めない細い帯になった。レビュー用に撮影するときは、各ステップを成功したユーザーのように答えさせ、レビュー対象の部分だけを撮る。

**検出の問い。** 読み手が見る通りに、その要素そのものを確認したか、それともソースの中で単語（またはコード）を見つけただけか？

**危険信号。**「ファイルに単語はある」「一行の修正だ」

**どうするか。**「これら三つの手順が、箇条書きとして」のように、正確な要素を確認する。そして、読み手が見る通りに、ページを少なくとも一度は見る。小さな修正も確認する。別のルールがそれを上書きすると、最も予想されていない場所だからだ。そして、ページで新しいリソース（コードブロック、固定ヘッダー）を初めて使うときは、モバイルでも見る。

### 45. エラーの道も、誰かが歩く

`from: 93409a9c` · `by: ai`

**要点。** すべてがうまくいくときに起きることだけをテストすると、間違える人が、その抜け穴を見つけてしまう。学習中には、間違えることこそが最も一般的なことである。

**例。** クエリのセルは、クエリが実行されたときにしか試行回数を数えなかった。タイプミスがあると、次に進むボタンは有効にならず、人は立ち往生した。テストは通っていた。いつもエラーのない最初のクエリを実行していたからである。

**検出の問い。** ユーザーが最もありそうな間違いをする（タイプミス、空の回答、二回のクリック）と、何が見えるか？ そして、ユーザーは進み続けられるか？

**危険信号。** 「正しい答えなら動く」

**どうするか。** 各コントロールについて三つの道をテストする。正しい道、最もよくある誤り、そして空の場合。三つとも、何が起きたかを伝え、ユーザーが進み続けられるようにする。

### 46. すべてのリクエストで動くものは、コンテンツと一緒に大きくなってはならない

`from: b7ad7ec2` · `by: ai`

**要点。** すべてのページで行うこと（すべてのコンテンツを読む、索引を再計算する）は、十ページなら少しの費用しかかからないが、百ページなら多くかかる。それは少しずつ大きくなり、「たまに」失敗し始めるまで誰も気づかない。

**例。** サイトのすべてのページが、目次を作るためにすべてのコンテンツを読んで解析していた。一ページだけなら 0.4 秒だった。しかしサイドバーは一度に約 40 件を要求していたので、合わせると 16 秒かかった。数か月後、ページを切り替えるとテストが失敗するようになり、その失敗はテストの問題に見えた。

**検出の問い。** このすべてのリクエストで動くものは、すべてのコンテンツを通るか？ それは今どれくらいかかり、二倍の量ならどれくらいか、そして多くのリクエストが同時に来たらどうか？

**危険信号。** 「ローカルでは速く読み込まれる」「たまにしか起きない失敗だ」

**どうするか。** 一ページだけではなく、コンパイルされたサーバーで、人々の使い方どおり、すべてのリクエストをまとめて測る。サーバーの稼働中に変わらないものはキャッシュする。そして、それを遅くした実際のケースで、その速さを測るテストを残す。

### 49. 一般的なルールは、特定のルールを黙って打ち負かしてはならない

`from: 4a81cf45` · `by: ai`

**要点。** すべてに当てはまるルール（グローバルなスタイル、デフォルト値）は、各部品が自分で決めたことを、何の警告もなく上書きしうる。

**例。** サイト全体のためのキーボードのフォーカススタイルには、独自の角丸が含まれていた。各コンポーネントのスタイルより優先されたため、ピル型のボタンは、キーボードでフォーカスすると形が変わった。マウスでは、フォーカスが現れないので、誰も気づかなかった。

**検出の問い。** この一般的なルールは、各部品が自分で決めている何かに触れるか？ 両者が衝突したら、どちらが勝つか？

**危険信号。** 「繰り返さなくていいように、グローバルにした」

**どうするか。** 一般的なルールには、自分のものだけに触れさせる（フォーカスの輪郭は触るが、形は触らない）。意図的に勝たせたいなら、その横にそう書く。そして、一般的な部品ではなく、最も異なる部品でテストする。

### VIDEO-1. 動画では、各操作は、ナレーションがそれを言う瞬間に重なる

`from: 93ac042f` · `by: ai`

**要点。** 画面が、声がそれを言うより前や後に何かをすると、視聴者は聞いていないものを見て、見ていないものを聞くことになる。言葉より前に起きるクリックは、その名前を伴わないクリックを教えてしまう。

**例。** コードで作られた、ナレーション付きの表計算の動画シリーズでは、各クリックは場面の中の割合の位置に置かれていた。教育のレビュアーは、声がそのオプション（サイドパネルの色）を名指しするより前に起きているクリックを見つけた。また、文が前置きで始まっているのに、カーソルがすでに最初のクリックをしている箇所もあった。そこから出たルールは、文が前置きで始まるなら、その区間にはクリックを置かず、各クリックは、それを名指す言葉の上に置く、というものだった。

**別の例。** 同じシリーズで、コースの持ち主が、動画が一つの考えから次の考えへ速すぎて飛ぶと言った。新しい考えが終わるところに、1〜1.5秒の静止した間を入れると、それが直った。

**検出の問い。** この場面の各クリックとキー入力は、ナレーションのどの言葉の上に来ているか？ その言葉がそれを名指ししているか？ 新しい考えはそれぞれ、次が始まる前に、静止した瞬間で終わっているか？

**危険信号。**「だいたいその辺りで言っている」「場面の割合で置いたから、合っている」

**どうするか。** 声が単語ごとのタイムスタンプを返さないなら、各操作は、その言葉が文の中のどこにあるか（その前にある文字数）で置き、静止画ではなく、完成した動画を実際の速さで確かめる。音声エンジンが単語のタイムスタンプを返すなら、操作はそれに合わせて置く。声を変えたり文を言い換えたりすると、すべての言葉のタイミングが動くので、場面をもう一度確かめる。新しい考えはそれぞれ、約一秒の短い静止で閉じ、それも実際の速さで判断する。

### VIDEO-2. 動画では、見せずに変わったものには印をつける

`from: c7d1a08d` · `by: ai`

**要点。** ある手順の効果が画面に見えないとき（末尾の空白を消す、数式をその値に変える）、その手順を見せる動画は、何もしていないように見える。視聴者はクリックして確かめることができない。だから動画は、何が変わったかに印をつけ、その印が見えるだけの時間、画面を止めておかなければならない。

**例。** 生成された動画は、表計算の列の余分な空白を取り除き、その結果を値だけとして貼り付ける方法を教えていた。整えた列は汚れた列とまったく同じに見え、値として貼り付けても、目に見える変化は何もなかった。コースの持ち主は動画を見て、変化に気づけないし、「値のみ」がなぜ重要なのかわからないと言った。直し方は、余分な空白のすべてにオレンジの点を付け、両方の列を並べた場面を入れ、元のセルからそれを読む数式へ矢印を引くことだった。それぞれ少しの間、画面を止めて見せるようにした。

**検出の問い。** 音を消しても、画面にはこの手順が何を変えたかが映っているか？ そして、それが見えるだけの長さ、画面がそこに留まるか？

**危険信号。**「ナレーションが説明している」「変化は微妙だが、ちゃんとある」

**どうするか。** 台本の手順ごとに、画面で何が変わるかを書き出す。目に見えて変わるものがなければ、印（点、数式バー、矢印、前後を並べた比較）を加え、その画面を少しの間止め、そして、その印はプログラムのものではなく動画の印だとナレーションで言う。

### WEB-2. 公開フォームには、初日からボットが来る

`from: 6a05ed7d` · `by: ai`

**要点。** インターネットに開かれたフォームは、人だけが入力するわけではない。自動送信を止めるものがなく、メッセージを読む側がそれを掃除できなければ、最初の迷惑メールの波が本物の顧客を埋もれさせる。

**例。** Web シミュレーションの両方の実行で、問い合わせフォームは、数秒のうちにスクリプトから 650 件のメッセージを受け付け、どれもが「ありがとう」と言っていた。管理者にはページも削除ボタンもなく、管理ページは高さが 100 万から 600 万ピクセルの間に膨らみ、モバイルでは、メッセージの本文が画面からはみ出した。どちらの場合も、構築者はそれを保留として記録していた。

**検出の問い。** 明日、千件の偽のメッセージが届いたら、持ち主はどうやって本物の一件を見つけ、残りをどうやって削除するのか？

**危険信号。** 「小さなサイトだから、誰も攻撃しない」「制限は後で追加する」

**どうするか。** 最初から、安価な歯止めを入れる。人が入力しない隠しフィールドと、アドレスごとの一分あたりの送信数の上限。そして、新しい順に並んだページを持つ管理画面と、削除または迷惑としてマークする手段。スクリプトで数百件のメッセージを送り、携帯電話で管理画面を開いてテストする。

### WEB-3. テストされていないフォールバックは、フォールバックではない

`from: c0e4cb66` · `by: ai`

**要点。** `method` と `action` を持つフォームは、JavaScript が失敗しても動くフォールバックを約束している。サーバーが JavaScript の期待する応答しか返さないなら、その約束は偽りで、人はコードを前に途方に暮れることになる。

**例。** Web シミュレーションの両方の実行で、フォームは JavaScript で送信され、`method="post"` が宣言されていた。JavaScript がない場合、一方の版では、サーバーが JSON の一行で送信を拒否し、メッセージは失われた。もう一方では、メッセージは保存されたが、空白のページに `{"ok":true}` だけが表示された。この二つ目の版の概要は、JavaScript なしでは送信しないと書いていた。

**検出の問い。** この JavaScript ファイルが読み込まれなかったら、送信したとき人は何を見るのか？

**危険信号。**「どうせみんな JavaScript を持っている」「念のため `action` は残しておこう」

**どうするか。** 二つのうち一つに決め、テストする。サーバーが通常の送信を受け付け、ページで応答する（またはお礼のページにリダイレクトする）か、あるいは、持っていないフォールバックを宣言しないか。JavaScript をオフにして、一度送信してみる。

### WEB-4. ボタンを無効にすると、フォーカスも一緒に消える

`from: 4dc9e2b6` · `by: ai`

**要点。** 送信中にボタンを無効にすると二重送信は防げるが、ボタンはフォーカスを失い、ブラウザはフォーカスをドキュメントに移す。キーボードを使っている人は、通知の後、最初からやり直すことになる。

**例。** Web シミュレーションの両方の実行で、送信するとボタンが無効になった。サーバーが拒否したメールアドレスでは、通知がボタンの下に現れ、フォーカスはドキュメントに移り、次の Tab でページ上の最初のリンクに移動した。直すべきフィールドからは遠く離れていた。

**検出の問い。** 送信のあと、成功しても失敗しても、フォーカスはどこに行き、次の Tab はどこへ進むか？

**危険信号。** 「二回送信できないように無効にしている」

**どうするか。** 送信が終わったら、人が続けるために必要な場所にフォーカスを置く。エラーのあるフィールド（`aria-invalid` とその横のメッセージでマークする）か、成功の通知に。あるいは、無効にせずに二重送信を防ぐ。`aria-disabled` とフラグを使う。キーボードだけを使って、エラーの修正まで一通り操作してみる。

### WEB-5. 試行回数の制限がないパスワードログインは、最も弱いパスワードと同じ強さしかない

`from: 0e974320` · `by: ai`

**要点。** 間違ったパスワードに全速力で答えるログインは、誰でも毎分何千回も試せてしまう。強い初期パスワードは、持ち主が自分のパスワードを設定するまで問題を隠しておく。しかし、設定されたパスワードが短くても、それを止めるものは何もない。

**例。** Web シミュレーションの再実行の両方の実行で、管理ページはパスワードを求めたが、失敗の回数を制限しなかった。間違ったパスワードを 200 回続けて送ると、一秒もかからず 200 回拒否されたが、どれもブロックされなかった。初期パスワードは長くてランダムだったが、構築した側の要約は持ち主に新しいパスワードの設定方法を教えており、それが長さを求める箇所はどこにもなかった。

**検出の問い。** このログインに対して、誰かが一分間に何回、間違ったパスワードを試せるか？ そして、五回目の後に何が起きるか？

**危険信号。** 「初期パスワードは強い」「管理ページだけだから」

**どうするか。** 繰り返される失敗を遅くするか、ブロックする。アドレスごと、アカウントごとに、待ち時間を少しずつ増やしていく。持ち主がパスワードを設定するときは、最低限の長さを求める。テストは、間違ったパスワードを二十回続けて送り、最後の数回が拒否されることを確かめて行う。
