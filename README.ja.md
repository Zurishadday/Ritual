# Ritual

[English](README.md) · [Español](README.es.md) · [Português](README.pt.md) · [Français](README.fr.md) · [中文](README.zh-CN.md) · **日本語** · [한국어](README.ko.md)

**Claude が間違えるのは一度だけ。Ritual は、それが最後になるようにします。**

Ritual は、どんなプロジェクトにも使える Claude Code プラグインです。考え方は一つです：**あらゆるミスはレッスンになり、あらゆるレッスンはルールになり、そしてあらゆるルールは、できる場合にはテストかガードになります。** 他のツールは学んだことを書き留めるだけですが、Ritual はそこから一歩進んで、それを検証します。テキストの中にしか存在しないルールは長いセッションの中で忘れられてしまいますが、自分で検証するルールは忘れられないからです。

Ritual には、実際のミスからそれぞれ生まれた 49 件のフィールドレッスンが含まれています。プロジェクトの種類ごとのパッケージもあり、そのレッスンは、モデルが何かを作って壊すのを観察した結果から来ています。そして、一つのコマンド `/ritual` があります。これは、セッションのミスをあなた自身のレッスンに変え、そのレッスンを、自分で強制されるルールに変えます。

## インストール

```bash
claude plugin marketplace add Zurishadday/Ritual
claude plugin install ritual@ritual
```

その後、プロジェクトで `/ritual` と入力します。初回は、依存関係から何を作っているかを検出し、一つだけ質問します（どのレッスンパッケージを有効にするか、そしてどの言語にするか）。そして `.ritual/` フォルダを作ります。それ以降は、三つのフックが何もしなくても動きます。

| フック | 何をするか | かかるコスト |
|---|---|---|
| **ガード** | プロジェクトがすでに失敗を見たコマンドをブロックし、代わりに何を使うかを示します。ルールは `.ritual/guard.json` にあり、それぞれに、ブロックするケースと通すケースが一つずつ付いています。 | ブロックするまでは何もかかりません。 |
| **ログ** | 失敗したすべてのコマンドと、あなたの訂正（「それは違う」「もう一度やって」）を、Claude が何に触れていたかとともに、その場で記録します。 | 何もかかりません。 |
| **質問** | セッションで初めて Claude がテスト、コンポーネント、スクリプト、ドキュメント、クエリを編集しようとしたとき、あるいはコマンドを実行したりコミットしようとしたりするとき、そのグループの検出の問いを Claude に示します。グループごと、セッションごとに一度です。 | グループとパッケージに応じて、グループ内のレッスンごとに一行。三行から十三行です。 |

これらは Claude の動作を変えることはありません。適切な瞬間に、プロジェクトがすでに学んだことを Claude の前に示すだけです。

## リチュアルの流れ

セッションを閉じるとき、あるいは痛手となったミスのあとに、`/ritual` と入力します。それはログを読み、次の順番で実行します。

0. 前回のリチュアルが残した**候補**を見直す：テストになれたのに、なれなかったもの。
1. **ミスを一覧にする。** まずログから始め、それぞれの原因を確認します。
2. **そのミスをどのレッスンがカバーしていたか、そして、なぜ発動しなかったかを探す。** まずミスのグループの中から探します。カバーしていたレッスンがあれば、その検出の問いや危険信号を研ぎ澄ませるか、例を加えます。
3. **誤検出を探す。** 何もないのに Claude を止めた質問や、間違っていたガードのブロックです。間違ったブロックは、ルールが必ず通すべきケースになります。
4. カバーするレッスンがない場合にのみ、**新しいレッスン**を、五つの部分とともに書きます。
5. 可能なところでは**はしごを登ります。** コマンドのパターンはガードルールになります。コードの性質や、レッスン名のテスト（本物のミスに対して失敗するところを先に見てから信頼します）もそうです。自動化できず、すでに二回壊れたものは、`CLAUDE.md` の一行になります。それ以外は、日付つきの候補のまま残ります。
6. すべてを同じコミットでまとめて保存し、チェッカーを実行します。
7. 例は匿名のまま残します。あるレッスンがどのプロジェクトにも当てはまるなら、ここで共有するための文面を提案します。自分から何かを公開することはありません。

そして `/ritual close` は、完了と言う前に、変更したグループの質問を変更内容と照らし合わせ、何が足りないかを伝えます。

## ライブラリ

レッスンは [`lessons/ja/`](lessons/ja/README.md) にあります（原文は英語で、[`lessons/en/`](lessons/en/README.md) にあります）。ミスが起きたときに何をしていたかによって、七つのグループに分かれています。

| グループ | 対象 |
|---|---|
| 執筆とドキュメント | ドキュメント、マニュアル、画面の文言、コンテンツ、プロンプト。 |
| 数値とデータ | ダッシュボード、レポート、モデル、表示されるあらゆる数値。 |
| テストとチェック | 自動テスト、バリデータ、レビュー、キャリブレーション。 |
| スクリプトとファイル | ファイルやデータを書き出す、生成する、変換するプログラム。 |
| インターフェースとデザイン | 画面、コンポーネント、スタイル、ページ。 |
| コンソールとツール | コマンド、サーバー、キャプチャ、そして邪魔をするツール。 |
| Git とプロセス | コミット、状態、保留中の作業、並行作業。 |

グループの上には、プロジェクトの種類ごとの**パッケージ**があります。これは、そのプロジェクトを作る場合にだけ当てはまるレッスンです。パッケージのレッスンは、グループのファイルの中に接頭辞付き（`WEB-1`）で置かれ、そのパッケージが有効なときにだけ、その質問が表示されます。セットアップ時に有効になり、`.ritual/config.json` で変更できます。

| パッケージ | レッスン |
|---|---|
| `web` | 4件：書き込みが途中で切れた後に失われるもの、公開フォームのボット、JavaScript を使わない場合のフォールバック、送信時のフォーカス。 |
| `apps`, `crm`, `ai` | 順次追加します。同じ方法で作ります。 |

すべてのレッスンは五つの部分から成り、必ず五つすべてがあります：**要点**、実際の、匿名の**例**、該当するケースと該当しないケースを分ける**検出の問い**、同じミスを再びする直前に自分に言う言葉である**危険信号**（あなたが自分に言う言葉です）、そして**どうするか**。番号は決して変わりません。冗長なレッスンは、別のものに統合済みとして印を付けるのであり、削除はしません。完全な形式は [`lessons/TEMPLATE.md`](lessons/TEMPLATE.md) にあります。

各レッスンには、その出典が書かれています：

- `field`：プロジェクトで実際に起きたミスで、その例が付いています。
- `lab`：[シミュレーション](simulations/README.md)の中で壊れたもので、どのモデルでいつかを書いています。誰かが自分のプロジェクトでそれを確認すると、`field` になります。
- `proposal`：目に見えて壊れることのないもの（セキュリティなど）だけで、公開された出典が付いています。

例として、レッスン 13 を挙げます：

> **誤りを一度も見ていないチェッカーは、何も検証していない。** いつも通るテストは、壊れているかもしれない。それを知る唯一の方法は、本物の誤りに対して失敗するところを見ることである。 *検出の問い：* このチェックを、実際にエラーが現れる形で、そして正しいケースに対して、テストしたか？ *危険信号：* 「もう通っているから、正しく設定されている」

Ritual は、このレッスンを自分自身にも当てはめています。このリポジトリのすべてのガードルール、すべてのチェッカー、すべてのフックには、そのケースが付いており、組み込まれる前に失敗するところを見ています。

## パッケージのレッスンは、シミュレーションから生まれる

プロジェクトの種類ごとのレッスンは、作り話ではありません。あるモデルが、Ritual を使わずに現実的な課題を作ります。別のセッションの別のモデルが、作られたものを実行し、何が壊れたかを証拠とともに記録します。壊れたものはレッスンとして入り、壊れなかったものは入りません。どの課題も二回実行されます。二回とも壊れたものはレッスンになり、一回だけ壊れたものは候補のままです。新しいモデルが出ると課題は再び実行され、もう壊れなくなったレッスンは、データとともに格下げされます。方法と課題は [`simulations/`](simulations/README.md) にあります。

最初のシミュレーションは、問い合わせフォームと管理ページを備えた、自転車修理店のウェブサイトでした。Sonnet が二回作りました。どちらの版も HTML を正しくエスケープし、リクエストを公開フォルダの中に保ち、同時に 300 件のメッセージにも耐えました。それでも、両方とも切断された書き込みの後に届いたメッセージを黙って失い、両方とも、後から片付ける手段のないまま、ボットから数百件のメッセージを受け付けていました。さらに一つは、テストが十回に一回失敗するにもかかわらず、通ったと報告していました。すべての発見は、残されたコードのそばに、証拠とともに [`simulations/web/runs/`](simulations/web/runs/2026-10-sonnet-2/FINDINGS.md) にあります。

Ritual も、自分のレッスンで検査されています。WEB-1 は、Ritual 自身のログにあった同じバグを見つけ、先に失敗するところを見たテストとともに修正されました。

## 貢献する

一番かんたんな方法は、**レッスンを確認すること**です。`lab` または `proposal` のレッスンが実際にあなたの身に起きたなら、匿名の例を添えて issue を開いてください。そのレッスンは `field` になり、希望すれば、あなたの名前とともに記載されます。

ほかにも次のことができます。

- **自分のレッスンを共有する。** 五つの部分、匿名の例、そして所属するグループ。`/ritual` が文面を書いてくれます。
- **足りないプロジェクトの種類について、シミュレーションの課題を提案する。**
- **翻訳をレビューする。** レッスンはモデルによって翻訳されており、各レッスンにその旨が書かれています（`by: ai`）。あなたがネイティブスピーカーなら、直して、GitHub のユーザー名で署名してください。手順は [`lessons/TRANSLATING.md`](lessons/TRANSLATING.md) にあります。
- **ガードルールを追加する。** あるいは、それが通すべきだったケースを追加する。

プルリクエストを開く前に：`npm test` を実行してください。これは、すべてのチェッカーとフックのキャリブレーションを実行し、すべてのレッスンが五つの部分を持つこと、そしてインデックスが最新であることを確認します（`node scripts/lessons.mjs --index` で再生成できます）。
